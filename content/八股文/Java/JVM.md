# JVM

### JVM 内存区域

**概念**：JVM 运行时数据区的划分

**详细解释**：
线程私有：程序计数器、虚拟机栈、本地方法栈。
线程共享：堆（存放对象实例）、方法区/元空间（存放类信息、常量）。
JDK 1.8 后方法区由永久代改为元空间（Metaspace），使用本地内存。

**问题**：说一下 JVM 的内存区域划分

**答案要点**：
1. 程序计数器：当前线程执行的字节码行号
2. 虚拟机栈：存放栈帧（局部变量表、操作数栈）
3. 堆：对象实例和数组，GC 主要区域
4. 方法区/元空间：类信息、常量池、静态变量

**常见陷阱**：
- ❌ 把永久代和元空间混为一谈
- ✅ 说清楚 JDK 版本差异

**追问**：
- Q: 哪些区域会发生 OOM？
- A: 堆（最常见）、栈（递归过深）、元空间（动态生成类过多）

### GC 算法

**概念**：自动回收不再使用的对象，释放内存

**详细解释**：
判断对象存活：引用计数（有循环引用问题）、可达性分析（GC Roots）。
回收算法：标记-清除、标记-复制、标记-整理。
分代收集：新生代用复制算法，老年代用标记-整理。

**问题**：说一下 JVM 的垃圾回收机制

**答案要点**：
1. 可达性分析：从 GC Roots 出发，不可达的对象被回收
2. GC Roots：栈帧引用、静态变量、常量、JNI 引用
3. 新生代：Eden + S0 + S1，Minor GC
4. 老年代：Full GC，STW 时间长

**常见陷阱**：
- ❌ 只说"引用计数"
- ✅ Java 用可达性分析，引用计数有循环引用问题

**追问**：
- Q: 什么是 STW？如何减少 STW 时间？
- A: Stop The World，所有线程暂停。使用 G1、ZGC 等低延迟收集器

### 常用收集器

**概念**：执行垃圾回收的具体实现

**详细解释**：
串行：Serial、Serial Old（单线程，STW）。
并行：Parallel Scavenge、Parallel Old（多线程，吞吐量优先）。
并发：CMS、G1、ZGC（低延迟，减少 STW）。

**问题**：说一下你了解的垃圾收集器

**答案要点**：
1. CMS：并发标记清除，低延迟，有碎片
2. G1：分 Region，可预测停顿时间
3. ZGC：JDK 11+，TB 级堆，STW < 10ms
4. Shenandoah：类似 ZGC，Red Hat 出品

**常见陷阱**：
- ❌ 只说名字，不说特点
- ✅ 结合场景：吞吐量 → Parallel，延迟 → G1/ZGC

**追问**：
- Q: JDK 8/11/17 默认收集器？
- A: JDK 8 是 Parallel，JDK 9+ 是 G1

### 类加载过程

**概念**：将 .class 文件加载到 JVM 内存的过程

**详细解释**：
加载 → 验证 → 准备 → 解析 → 初始化。
双亲委派：先委托父加载器加载，父加载器无法加载才自己加载。
打破双亲委派：SPI、OSGi、Tomcat 等场景。

**问题**：说一下类加载过程和双亲委派机制

**答案要点**：
1. 加载：读取字节码，生成 Class 对象
2. 验证：校验字节码格式
3. 准备：为静态变量分配内存，赋默认值
4. 初始化：执行 <clinit>，赋初始值

**常见陷阱**：
- ❌ 漏掉"准备阶段赋默认值"
- ✅ 准备阶段 int 默认 0，初始化阶段才赋代码中的值

**追问**：
- Q: 为什么要双亲委派？
- A: 安全（防止篡改核心类）+ 避免重复加载
