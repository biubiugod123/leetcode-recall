# 并发编程

### synchronized 原理

**概念**：Java 内置的同步机制，可修饰方法或代码块

**详细解释**：
synchronized 基于 Monitor（监视器锁）实现。
JDK 1.6 后引入锁升级优化：偏向锁 → 轻量级锁 → 重量级锁。
对象头的 Mark Word 存储锁状态信息。

**问题**：说一下 synchronized 的实现原理和锁升级过程

**答案要点**：
1. 底层：monitorenter/monitorexit 指令
2. 锁升级：无锁 → 偏向锁 → 轻量级锁（CAS自旋）→ 重量级锁
3. 偏向锁：记录线程 ID，同一线程无需 CAS
4. 轻量级锁：CAS 自旋，竞争不激烈时高效

**对比**：
- vs ReentrantLock：后者可中断、可超时、可公平

**常见陷阱**：
- ❌ 说 synchronized 很重，性能差
- ✅ JDK 1.6 后优化很大，轻量级场景性能接近 CAS

**追问**：
- Q: 什么情况下锁会升级？
- A: 偏向锁遇到竞争升级为轻量级锁，自旋超过阈值升级为重量级锁

### volatile 原理

**概念**：保证变量的可见性和禁止指令重排序

**详细解释**：
volatile 通过内存屏障实现：写操作后加 StoreLoad 屏障，读操作前加 LoadLoad 屏障。
可见性：写入主内存，其他线程缓存失效。
有序性：禁止编译器和 CPU 重排序。

**问题**：volatile 能保证什么？不能保证什么？

**答案要点**：
1. 保证可见性：修改立即刷新到主内存
2. 保证有序性：禁止指令重排
3. 不保证原子性：i++ 不是原子操作

**对比**：
- vs synchronized：volatile 更轻量，但不保证原子性

**常见陷阱**：
- ❌ 认为 volatile 可以替代锁
- ✅ volatile 适用于一写多读，或状态标志位

**追问**：
- Q: 双重检查锁为什么需要 volatile？
- A: 防止指令重排：分配内存 → 初始化 → 赋值引用 可能被重排

### ThreadPoolExecutor

**概念**：管理和复用线程的执行器，避免频繁创建销毁线程

**详细解释**：
核心参数：corePoolSize、maxPoolSize、keepAliveTime、workQueue、handler。
执行流程：核心线程 → 队列 → 最大线程 → 拒绝策略。
常用实现：FixedThreadPool、CachedThreadPool、ScheduledThreadPool。

**问题**：说一下线程池的核心参数和执行流程

**答案要点**：
1. corePoolSize：核心线程数，即使空闲也不回收
2. maxPoolSize：最大线程数
3. workQueue：阻塞队列，存放等待任务
4. 流程：任务 → 核心线程 → 队列 → 非核心线程 → 拒绝

**常见陷阱**：
- ❌ 直接用 Executors 创建（OOM 风险）
- ✅ 手动创建 ThreadPoolExecutor，控制队列大小

**追问**：
- Q: 四种拒绝策略？
- A: AbortPolicy（抛异常）、CallerRunsPolicy（调用者执行）、DiscardPolicy（丢弃）、DiscardOldestPolicy（丢弃最老）

### AbstractQueuedSynchronizer

**概念**：Java 并发包的基础框架，ReentrantLock、Semaphore 等都基于它

**详细解释**：
AQS 维护一个 volatile int state 表示同步状态，和一个 FIFO 双向队列存放等待线程。
子类通过重写 tryAcquire/tryRelease 实现自定义同步器。
支持独占模式和共享模式。

**问题**：说一下 AQS 的原理

**答案要点**：
1. state：同步状态，volatile 修饰
2. CLH 队列：双向链表，存放等待线程
3. 获取锁：CAS 修改 state，失败则入队等待
4. 释放锁：修改 state，唤醒后继节点

**常见陷阱**：
- ❌ 只说 CAS
- ✅ CAS + 队列 + park/unpark

**追问**：
- Q: ReentrantLock 的公平锁和非公平锁区别？
- A: 公平锁先检查队列，非公平锁直接 CAS 竞争
