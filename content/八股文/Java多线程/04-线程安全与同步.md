# 线程安全与同步

### 竞态条件与线程干扰

**概念**：多个线程通过共享资源通信，高效但容易出错，这类问题统称竞态条件（race conditions），包括线程干扰（thread interference）和内存一致性错误（memory consistency errors）

**一句话**：线程干扰是指两个线程对同一份数据的多步操作交错执行；比如 c++ 在 JVM 里分成"读取 c、加 1、写回 c"三步，不是原子操作，线程 A 执行 increment、线程 B 执行 decrement 时，一方的结果可能被另一方覆盖，最终结果不确定。

**详细解释**：
Thread Safety：Threads primarily communicate by sharing access to common resources；This form of communication is efficient and fast, but also error-prone without proper care；Multi-threaded communication can lead to various issues collectively known as race conditions。
Thread Interference：两个线程同时操作同一个对象；Interference happens when two operations, running in different threads, but acting on the same data, interleave. This means that the two operations consist of multiple steps, and the sequences of steps overlap。
c++ 被 JVM 分解为：Retrieve the current value of c → Increment the retrieved value by 1 → Store the incremented value back in c，所以 "c++ is not atomic"。
一种交错：c = 0，A 读到 0，B 读到 0，A 写回 1，B 写回 -1，A 的修改丢失。
解决：synchronized、Lock，或者用原子类 AtomicInteger。

**问题**：什么是竞态条件？为什么 count++ 在多线程下不安全？

**答案要点**：
1. 多个线程共享数据、并且操作交错执行时会出现竞态条件
2. 包括线程干扰和内存一致性错误
3. count++ 不是原子操作，分为读取、加一、写回三步
4. 两个线程的步骤交错时，一个线程的修改会被另一个覆盖
5. 用 synchronized、Lock 或 AtomicInteger 解决

**常见陷阱**：
- ❌ 认为一行代码就是一个原子操作
- ✅ c++、i = i + 1、if (x == null) x = new X() 都由多步组成，可能被打断
- ❌ 以为把变量声明为 volatile 就能让 c++ 线程安全
- ✅ volatile 只保证可见性，不保证复合操作的原子性

**追问**：
- Q: 多线程调用没有同步的 increment 各 10000 次，结果一定小于 20000 吗？
- A: 不一定，通常会小于 20000，但也可能恰好等于；结果不确定正是问题所在

**代码题**：下面代码输出什么？

```java
class Counter {
    private int c = 0;
    public synchronized void increment() { c++; }
    public synchronized void decrement() { c--; }
    public synchronized int value() { return c; }
}
Counter counter = new Counter();
Thread a = new Thread(() -> { for (int i = 0; i < 10000; i++) counter.increment(); });
Thread b = new Thread(() -> { for (int i = 0; i < 10000; i++) counter.decrement(); });
a.start();
b.start();
a.join();
b.join();
System.out.println(counter.value());
```

- [x] 0
- [ ] 不确定，可能是任何值
- [ ] 10000
- [ ] -10000

解析：三个方法都加了 synchronized，同一时刻只有一个线程能修改 c，不会互相覆盖，加减各 10000 次后结果一定是 0；去掉 synchronized 结果就不确定了。

**判断题**：
- ✅ c++ 不是原子操作 —— 它包括读取、加一、写回三个步骤
- ❌ 只要两个线程访问的是同一个对象，就一定会发生线程干扰 —— 只读、或者操作被正确同步时不会出问题

### 内存可见性与 volatile

**概念**：内存一致性错误（memory consistency error）是指不同线程看到的共享数据不一致；volatile 关键字保证变量的修改对其他线程立即可见

**一句话**：为了性能，CPU 和 JVM 会缓存变量的值、重排指令，一个线程修改了数据，另一个线程可能还在读过期的缓存；volatile 保证读写都直接针对主内存（可见性），并禁止相关的指令重排，但不保证 c++ 这类复合操作的原子性。

**详细解释**：
A memory consistency error occurs when different threads have inconsistent views of shared data。
Why it happens：Modern CPUs and the JVM may cache values or reorder instructions for performance；If thread 1 changes some data, other threads may still see an expired, cached copy of the data。
volatile keyword：Declaring a variable as volatile ensures that all reads go directly to main memory (not a thread's cache)；All writes are immediately flushed to main memory（课件的简化说法）。
更准确地说：volatile 写和之后对同一变量的 volatile 读之间建立 happens-before 关系，保证可见性和有序性；但不保证原子性。
典型用法：用 volatile boolean running 作为线程停止标志；双重检查锁单例里的 instance 字段。

**问题**：volatile 有什么作用？它能保证线程安全吗？

**答案要点**：
1. 内存一致性错误：线程读到了其他线程修改前的旧值
2. 原因：CPU 缓存、编译器和 CPU 的指令重排
3. volatile 保证可见性：写入后其他线程立即能读到
4. volatile 禁止相关的指令重排（有序性）
5. volatile 不保证原子性，c++ 仍然不安全，需要 synchronized 或原子类

**对比**：
| | volatile | synchronized |
|---|---|---|
| 可见性 | 保证 | 保证 |
| 原子性 | 不保证 | 保证 |
| 有序性 | 禁止相关重排 | 临界区内串行执行 |
| 是否阻塞 | 不阻塞 | 拿不到锁会阻塞 |
| 修饰对象 | 变量 | 方法、代码块 |

**常见陷阱**：
- ❌ 用 volatile int count 做多线程计数器
- ✅ count++ 不是原子的，要用 AtomicInteger 或加锁
- ❌ 认为 volatile 能代替 synchronized
- ✅ volatile 只适合"一个线程写、多个线程读"或状态标志这类场景

**追问**：
- Q: 不加 volatile 的停止标志会有什么问题？
- A: 工作线程可能一直读自己缓存里的 false，看不到主线程把标志改成 true，导致线程永远停不下来

**判断题**：
- ✅ volatile 可以保证一个线程对变量的修改对其他线程立即可见 —— 这是它的可见性保证
- ❌ 把计数器声明为 volatile，多个线程同时 count++ 就是线程安全的 —— volatile 不保证复合操作的原子性

### synchronized 关键字

**概念**：synchronized 是 Java 防止线程安全问题的同步工具，可以修饰方法（synchronized method）或代码块（synchronized block）；每个对象都有一把内置锁（intrinsic lock），进入同步代码前必须先拿到这把锁

**一句话**：一个线程在执行某个对象的 synchronized 方法时，其他线程调用同一个对象的任何 synchronized 方法都会被阻塞；synchronized 实例方法锁的是 this，static synchronized 方法锁的是类的 Class 对象，同步块可以锁任意指定对象、只锁需要保护的那几行；退出同步代码时建立 happens-before 关系，所以它同时保证原子性和可见性，并且是可重入的。

**详细解释**：
Synchronization：The tool needed to prevent these thread safety issues；两种方式：Synchronized method、Synchronized block。
```java
public synchronized void increment() {
    c++;          // 锁 this
}
public void decrement() {
    synchronized (this) {
        c--;      // 只锁这一段
    }
}
```
Synchronized Keyword：When one thread is executing a synchronized method on an object, other threads attempting to invoke any synchronized method on the same object are blocked until the first thread finishes；Upon exiting a synchronized method, a happens-before relationship is established with any subsequent synchronized method calls on the same object；each object has an intrinsic lock, and synchronized methods require acquiring that lock before proceeding。
Synchronized Block：can be used to perform synchronization on any specific resource of a part of the method；A synchronized method is essentially a special case of a synchronized block that locks on this for the entire method。
可重入：同一个线程已经持有锁时，再进入同一把锁保护的代码不会把自己锁住。

**问题**：synchronized 的原理和用法是什么？修饰实例方法和静态方法有什么区别？

**答案要点**：
1. 每个对象都有一把内置锁，进入 synchronized 代码前要先获取
2. 实例方法锁 this，static 方法锁类的 Class 对象，同步块锁指定的对象
3. 同一时刻只有一个线程能持有同一把锁，其他线程进入 BLOCKED
4. 保证原子性和可见性（退出时建立 happens-before）
5. 可重入；同步块锁的范围更小，性能更好

**对比**：
| 写法 | 锁的是什么 |
|---|---|
| synchronized 实例方法 | 当前对象 this |
| static synchronized 方法 | 类的 Class 对象（Xxx.class） |
| synchronized (obj) { } | 指定的对象 obj |

**常见陷阱**：
- ❌ 认为两个不同对象的 synchronized 实例方法也会互相阻塞
- ✅ 锁的是各自的 this，不同对象之间互不影响
- ❌ 认为 static synchronized 方法和实例 synchronized 方法用的是同一把锁
- ✅ 一个锁 Class 对象，一个锁 this，可以同时执行

**追问**：
- Q: synchronized 和 ReentrantLock 有什么区别？
- A: synchronized 是关键字，自动加锁解锁；ReentrantLock 需要手动 lock / unlock（放在 finally 里），但支持 tryLock、超时、可中断、公平锁和多个条件变量

**代码题**：下面代码输出什么？

```java
class Account {
    private int balance = 0;
    public synchronized void deposit() { balance++; }
    public synchronized void depositTwice() { deposit(); deposit(); }
    public synchronized int getBalance() { return balance; }
}
Account acc = new Account();
Thread t = new Thread(acc::depositTwice);
t.start();
t.join();
System.out.println(acc.getBalance());
```

- [x] 2
- [ ] 程序死锁，没有输出
- [ ] 1
- [ ] 0

解析：synchronized 是可重入的：线程在 depositTwice 里已经持有 acc 的锁，再调用同一把锁保护的 deposit() 可以直接进入，不会把自己锁住，余额加了两次。

**代码题**：下面代码输出什么？

```java
java.util.concurrent.atomic.AtomicInteger count = new java.util.concurrent.atomic.AtomicInteger();
Runnable task = () -> { for (int i = 0; i < 10000; i++) count.incrementAndGet(); };
Thread t1 = new Thread(task);
Thread t2 = new Thread(task);
t1.start();
t2.start();
t1.join();
t2.join();
System.out.println(count.get());
```

- [x] 20000
- [ ] 不确定，通常小于 20000
- [ ] 10000
- [ ] 0

解析：AtomicInteger 的 incrementAndGet 是原子操作（基于 CAS），不加锁也不会丢失更新，两个线程各加 10000 次，结果一定是 20000。

**判断题**：
- ✅ synchronized 修饰实例方法时，锁的是当前对象 this —— static 方法锁的是 Class 对象
- ❌ 一个线程持有某个对象的锁时，不能再次进入这个对象的其他 synchronized 方法 —— synchronized 是可重入的
