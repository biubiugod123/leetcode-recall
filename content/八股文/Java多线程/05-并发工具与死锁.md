# 并发工具与死锁

### java.util.concurrent 常用工具

**概念**：java.util.concurrent 包提供了并发编程常用的类和接口，比如 ConcurrentHashMap、ReentrantLock、AtomicInteger、BlockingQueue

**一句话**：ConcurrentHashMap 是线程安全的高性能 HashMap；ReentrantLock 是比 synchronized 更灵活的可重入锁（tryLock、超时、可中断、公平锁）；AtomicInteger 用 CAS 实现无锁的原子加减；BlockingQueue 在队列满时让 put 等待、空时让 take 等待，天然适合生产者-消费者。

**详细解释**：
java.util.concurrent：Utility class, includes some useful interfaces in concurrent programming：ConcurrentHashMap、ReentrantLock、AtomicInteger、BlockingQueue。
ReentrantLock 的标准写法：
```java
lock.lock();
try {
    // 临界区
} finally {
    lock.unlock();   // 一定要在 finally 里释放
}
```
AtomicInteger：incrementAndGet、getAndIncrement、compareAndSet；CAS（Compare-And-Swap）比较内存值和预期值，相等才更新，失败就重试。
BlockingQueue：ArrayBlockingQueue、LinkedBlockingQueue；put / take 会阻塞，offer / poll 可以带超时。
这个包里还有线程池（ExecutorService）、CountDownLatch、Semaphore 等，后面的课会讲。

**问题**：java.util.concurrent 包里有哪些常用工具？分别解决什么问题？

**答案要点**：
1. ConcurrentHashMap：线程安全的 Map，锁粒度细、性能好
2. ReentrantLock：可重入锁，支持 tryLock、超时、可中断、公平锁
3. AtomicInteger：基于 CAS 的原子操作，适合计数器
4. BlockingQueue：满时 put 阻塞、空时 take 阻塞，用于生产者-消费者
5. 还有线程池、CountDownLatch、Semaphore 等工具

**对比**：
| 工具 | 解决的问题 |
|---|---|
| ConcurrentHashMap | 多线程读写 Map |
| ReentrantLock | 需要比 synchronized 更灵活的锁 |
| AtomicInteger | 无锁的原子计数 |
| BlockingQueue | 线程之间安全地传递数据 |

**常见陷阱**：
- ❌ 使用 ReentrantLock 时，unlock 没写在 finally 里
- ✅ 临界区抛异常时锁不会被释放，其他线程永远拿不到锁

**追问**：
- Q: CAS 有什么问题？
- A: ABA 问题（值从 A 变 B 又变回 A，CAS 察觉不到，可以用带版本号的 AtomicStampedReference 解决）；高竞争时自旋重试会浪费 CPU

**代码题**：下面代码输出什么？

```java
java.util.concurrent.BlockingQueue<Integer> queue = new java.util.concurrent.ArrayBlockingQueue<>(2);
Thread producer = new Thread(() -> {
    try {
        for (int i = 1; i <= 4; i++) queue.put(i);
    } catch (InterruptedException e) { }
});
producer.start();
int sum = 0;
for (int i = 0; i < 4; i++) sum += queue.take();
producer.join();
System.out.println(sum + " " + queue.size());
```

- [x] 10 0
- [ ] 3 2
- [ ] 10 2
- [ ] 程序一直阻塞

解析：队列容量是 2，生产者放满后 put 会阻塞，等主线程 take 走元素再继续放；主线程 take 4 次，拿到 1+2+3+4 = 10，最后队列为空。

**代码题**：下面代码输出什么？

```java
java.util.concurrent.atomic.AtomicInteger n = new java.util.concurrent.atomic.AtomicInteger(5);
System.out.println(n.getAndIncrement() + " " + n.incrementAndGet() + " " + n.compareAndSet(7, 10) + " " + n.compareAndSet(7, 20) + " " + n.get());
```

- [x] 5 7 true false 10
- [ ] 6 7 true false 10
- [ ] 5 6 true true 20
- [ ] 5 7 false false 7

解析：getAndIncrement 返回旧值 5 再加到 6；incrementAndGet 先加到 7 再返回 7；compareAndSet(7, 10) 当前值是 7，更新成功；compareAndSet(7, 20) 当前值已是 10，失败；最终是 10。

**判断题**：
- ✅ BlockingQueue 的 take() 在队列为空时会阻塞等待 —— 适合实现生产者-消费者
- ❌ ReentrantLock 在代码块结束时会自动释放锁 —— 必须手动 unlock，一般写在 finally 里

### HashMap 的线程安全

**概念**：HashMap 不是线程安全的；多线程环境下可以用 Hashtable、Collections.synchronizedMap 或 ConcurrentHashMap

**一句话**：线程安全是指多个线程同时访问时，不需要额外同步也能得到正确结果；HashMap 并发 put 可能丢数据；Hashtable（Java 1.0 的老类）和 synchronizedMap 都是整张表一把锁，同一时刻只有一个线程能访问；ConcurrentHashMap 锁到 bucket 级别，不同 bucket 可以并发修改，读操作基本不加锁，性能最好，但不允许 null 的 key 和 value。

**详细解释**：
Is HashMap thread safe in Java？不是；比如两个线程同时 put 到同一个 bucket，可能互相覆盖；同时扩容也可能出问题（Java 7 头插法并发扩容甚至会形成环形链表导致死循环）。
Other implementations：Hashtable（legacy class from Java 1.0，课件写作 HashTable）；SynchronizedMap（integrated in Collections utility class）；ConcurrentHashMap（bucket-level lock, better performance）。
课件的图：HashMap 两个线程直接同时进入；Hashtable、SynchronizedMap 整个表一把锁，Thread 2 等 Thread 1；ConcurrentHashMap 多个线程可以同时读，只有写同一段时才需要等待。
ConcurrentHashMap 的实现：Java 7 用分段锁（Segment）；Java 8 改成 CAS + 对 bucket 头节点加 synchronized，锁粒度更细。
复合操作（先 get 再 put）即使用 ConcurrentHashMap 也不是原子的，要用 putIfAbsent、computeIfAbsent、merge 这类原子方法。

**问题**：HashMap 是线程安全的吗？Hashtable、synchronizedMap、ConcurrentHashMap 有什么区别？

**答案要点**：
1. HashMap 不是线程安全的，并发 put 可能丢数据
2. Hashtable：老类，所有方法加锁，整张表一把锁
3. Collections.synchronizedMap：包装任意 Map，同样整张表一把锁
4. ConcurrentHashMap：锁到 bucket 级别（Java 8 用 CAS + synchronized），并发性能最好
5. Hashtable 和 ConcurrentHashMap 都不允许 null key / value

**对比**：
| 实现 | 锁粒度 | null key / value | 性能 |
|---|---|---|---|
| HashMap | 无锁，不安全 | 允许 | 单线程最快 |
| Hashtable | 整张表 | 不允许 | 低 |
| Collections.synchronizedMap | 整张表 | 取决于被包装的 Map | 低 |
| ConcurrentHashMap | bucket 级别 | 不允许 | 高 |

**常见陷阱**：
- ❌ 用了 ConcurrentHashMap 就以为"先判断再 put"也是线程安全的
- ✅ 两步操作之间可能被插入，要用 putIfAbsent / computeIfAbsent / merge

**追问**：
- Q: ConcurrentHashMap 为什么不允许 null？
- A: 并发环境下 get 返回 null 时无法区分"key 不存在"和"值就是 null"，又没法像单线程那样先 containsKey 再 get 来确认，所以干脆禁止

**代码题**：下面代码运行结果是什么？

```java
Map<String, Integer> map = new java.util.concurrent.ConcurrentHashMap<>();
map.put("a", 1);
map.put(null, 2);
System.out.println(map.size());
```

- [ ] 2
- [ ] 1
- [x] 抛出 NullPointerException
- [ ] 编译错误

解析：ConcurrentHashMap 不允许 null 作为 key 或 value，put(null, 2) 抛出 NullPointerException；HashMap 才允许一个 null key。

**代码题**：下面代码输出什么？

```java
Map<String, Integer> counts = new java.util.concurrent.ConcurrentHashMap<>();
Runnable task = () -> { for (int i = 0; i < 1000; i++) counts.merge("hits", 1, Integer::sum); };
Thread t1 = new Thread(task);
Thread t2 = new Thread(task);
t1.start();
t2.start();
t1.join();
t2.join();
System.out.println(counts.get("hits"));
```

- [x] 2000
- [ ] 不确定，通常小于 2000
- [ ] 1000
- [ ] 抛出 ConcurrentModificationException

解析：merge 是 ConcurrentHashMap 提供的原子方法，"读出旧值、加 1、写回"作为一个整体完成，不会丢失更新，结果一定是 2000。

**判断题**：
- ✅ ConcurrentHashMap 比 Hashtable 的并发性能更好 —— 锁粒度是 bucket 级别，而不是整张表
- ❌ HashMap 是线程安全的，只是性能比 ConcurrentHashMap 差 —— HashMap 不是线程安全的

### 死锁

**概念**：死锁（Deadlock）是两个或多个线程永远阻塞、互相等待对方释放锁的情况

**一句话**：线程 A 持有资源 1 等资源 2，线程 B 持有资源 2 等资源 1，谁也等不到；死锁需要互斥、持有并等待、不可抢占、循环等待四个条件同时满足，破坏其中一个就能避免；常用办法是所有线程按相同顺序加锁、用 tryLock 带超时并重试、尽量减少同时持有的锁。

**详细解释**：
Deadlock describes a situation where two or more threads are blocked forever, waiting for each other to release the lock。
Necessary Conditions：
Mutual Exclusion：only 1 process can use a resource at a given time
Hold and Wait：持有一个资源的同时等待另一个
No Preemption：资源不能被强行抢走
Circular Wait：线程之间形成循环等待
Solutions：Try lock with timeout & retry；Lock Ordering；Minimize number of locks a thread needs at once ...
排查：用 jstack 或 jconsole 查看线程栈，会提示 "Found one Java-level deadlock"。

**问题**：什么是死锁？产生死锁的必要条件是什么？怎么避免？

**答案要点**：
1. 死锁：多个线程互相等待对方释放锁，永远阻塞
2. 四个必要条件：互斥、持有并等待、不可抢占、循环等待
3. 按固定顺序加锁，破坏循环等待
4. 用 tryLock 加超时，拿不到就释放已有的锁并重试
5. 减少同时持有的锁的数量，缩小锁的范围

**对比**：
| 必要条件 | 破坏它的办法 |
|---|---|
| 互斥 | 用无锁结构（很难完全避免） |
| 持有并等待 | 一次性申请所有需要的锁 |
| 不可抢占 | tryLock 超时后主动释放已持有的锁 |
| 循环等待 | 所有线程按相同顺序加锁 |

**常见陷阱**：
- ❌ 两个方法分别按 A→B 和 B→A 的顺序加锁
- ✅ 所有地方都按同一个顺序（比如按账户 id 从小到大）加锁

**追问**：
- Q: 转账时同时锁住转出和转入两个账户，怎么避免死锁？
- A: 按账户 id 排序后再加锁：总是先锁 id 小的账户，再锁 id 大的，这样不会形成循环等待

**判断题**：
- ✅ 所有线程按相同的顺序获取锁可以避免死锁 —— 破坏了循环等待条件
- ❌ 只要满足互斥条件就一定会发生死锁 —— 必须四个条件同时满足才会死锁
