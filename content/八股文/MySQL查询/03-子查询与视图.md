# 子查询与视图

### 子查询的分类与规则

**概念**：子查询是嵌套在 SELECT、INSERT、UPDATE、DELETE 语句或另一个子查询里的查询，必须写在括号里；按返回结果分为标量子查询、列子查询和表子查询，按是否引用外层查询的列分为非相关子查询和相关子查询

**一句话**：标量子查询返回一行一列，可以直接和值比较（score > (SELECT AVG(score) ...)）；列子查询返回一列多行，配合 IN 使用；表子查询放在 FROM 里当临时表；子查询能出现在 WHERE、FROM、SELECT 列表，也能用在 INSERT ... SELECT、UPDATE、DELETE 里；MySQL 不允许在 UPDATE / DELETE 的子查询里直接查询正在修改的那张表。

**详细解释**：
A subquery is a query that is nested inside a SELECT, INSERT, UPDATE, DELETE statement or inside another subquery；Subqueries must be written in parentheses；Subqueries must include the SELECT clause and the FROM clause（一般如此；MySQL 里 (SELECT 1) 这种不带 FROM 的标量子查询其实也合法）。
课件用的表：LIKES(ID, DRINKER, COFFEE)、FREQUENTS(ID, DRINKER, CAFE)、SERVES(CAFE, COFFEE)。
标量子查询返回了多行时，MySQL 报错 Subquery returns more than 1 row；和多行比较要用 IN、EXISTS，或者先聚合成一个值。
非相关子查询：不依赖外层，可以单独执行，只算一次；相关子查询：引用外层的列，外层每一行都要重新算一次。
MySQL 的限制：DELETE FROM rates WHERE score < (SELECT AVG(score) FROM rates) 会报错（You can't specify target table for update in FROM clause），要把子查询再包一层派生表，或者先把值查出来。

**问题**：子查询有哪几种？分别用在什么地方？

**答案要点**：
1. 子查询写在括号里，可以嵌套在 SELECT、INSERT、UPDATE、DELETE 和其他子查询中
2. 标量子查询（一行一列）：直接用 =、>、< 比较
3. 列子查询（一列多行）：配合 IN / NOT IN / EXISTS
4. 表子查询：放在 FROM 中当派生表，必须起别名
5. 非相关子查询只执行一次；相关子查询引用外层列，外层每行执行一次

**对比**：
| 类型 | 返回 | 常见位置 | 例子 |
|---|---|---|---|
| 标量子查询 | 一行一列 | WHERE、SELECT 列表 | score > (SELECT AVG(score) FROM rates) |
| 列子查询 | 一列多行 | WHERE ... IN | drinker IN (SELECT drinker FROM likes ...) |
| 表子查询 | 多行多列 | FROM | FROM (SELECT ...) AS t |

**常见陷阱**：
- ❌ 用 = 去比较一个会返回多行的子查询
- ✅ MySQL 会报 Subquery returns more than 1 row，要改用 IN，或者让子查询只返回一个值
- ❌ 在 DELETE / UPDATE 的子查询里直接查询要修改的同一张表
- ✅ MySQL 不允许，要把子查询包成派生表：WHERE score < (SELECT a FROM (SELECT AVG(score) AS a FROM rates) t)

**追问**：
- Q: SELECT 列表里的子查询有什么要求？
- A: 只能是标量子查询，每一行只能返回一个值；如果是相关子查询，外层每一行都会执行一次，数据量大时可以考虑改成 JOIN + GROUP BY

- ✅ 子查询必须写在括号里 —— 课件：Subqueries must be written in parentheses
- ❌ 子查询只能出现在 SELECT 语句的 WHERE 子句中 —— 子查询还能出现在 FROM、SELECT 列表中，也能嵌套在 INSERT、UPDATE、DELETE 里

### IN 与非相关子查询

**概念**：非相关子查询（non-correlated subquery）不引用外层查询的列，可以单独执行，数据库只需要执行一次，再拿结果给外层用，常和 IN 搭配

**一句话**：课件例子"谁同时喜欢 Cold Brew 和 Espresso"：外层找喜欢 Cold Brew 的人，再用 IN 检查他是否在"喜欢 Espresso 的人"这个子查询结果里；不能写成 coffee = 'Cold Brew' AND coffee = 'Espresso'（同一行不可能等于两个值），也不能写成 IN ('Cold Brew', 'Espresso')（那是喜欢任意一种）；很多子查询可以改写成 JOIN。

**详细解释**：
Subquery Example 1 with IN (non-correlated subquery)：Who likes 'Cold Brew' and 'Espresso'?
```sql
SELECT DISTINCT l.drinker
FROM likes l
WHERE l.coffee = 'Cold Brew'
  AND l.drinker IN (
    SELECT l2.drinker
    FROM likes l2
    WHERE l2.coffee = 'Espresso');
```
数据：1 Simon Mocha；2 Ethan Cappuccino；3 Kason Cold Brew；4 Kason Espresso；5 Fiona Mocha。结果：Kason。
Many subqueries can be written as JOIN：
```sql
SELECT DISTINCT l.drinker
FROM likes l
JOIN likes l2 ON l.drinker = l2.drinker
WHERE l.coffee = 'Cold Brew' AND l2.coffee = 'Espresso';
```
"同时满足两个条件"涉及同一个人的两行数据，单行的 WHERE 做不到，要用子查询、自连接，或者 GROUP BY drinker HAVING COUNT(DISTINCT coffee) = 2。

**问题**：什么是非相关子查询？"同时喜欢两种咖啡的人"该怎么查？

**答案要点**：
1. 非相关子查询不引用外层的列，可以单独运行
2. 只执行一次，结果交给外层的 IN 使用
3. "同时满足"涉及多行，用 IN 子查询、自连接或 GROUP BY + HAVING
4. coffee = A AND coffee = B 对单行永远不成立
5. 很多 IN 子查询可以改写成 JOIN，结果一样

**对比**：
| 写法 | 含义 | 结果 |
|---|---|---|
| coffee = 'Cold Brew' AND coffee = 'Espresso' | 同一行同时等于两个值 | 空 |
| coffee IN ('Cold Brew', 'Espresso') | 喜欢其中任意一种 | Kason（两行） |
| coffee = 'Cold Brew' AND drinker IN (喜欢 Espresso 的人) | 两种都喜欢 | Kason |

**常见陷阱**：
- ❌ 把"同时喜欢 A 和 B"写成 WHERE coffee = 'A' AND coffee = 'B'
- ✅ 一行只有一个 coffee 值，结果永远为空，要跨行判断
- ❌ 用 IN 子查询但不加 DISTINCT，以为一个人只会出现一次
- ✅ 外层表里同一个人有多行满足条件时会重复出现，需要的话加 DISTINCT

**追问**：
- Q: IN 子查询和 JOIN 改写，结果一定一样吗？
- A: 不一定：JOIN 时右表有重复值会让左表的行重复，IN 不会；所以 JOIN 改写通常要加 DISTINCT

**代码题**：下面 SQL 执行后，最后一条查询的结果是什么？

```sql

INSERT INTO likes VALUES (1, 'Simon', 'Mocha'), (2, 'Ethan', 'Cappuccino'), (3, 'Kason', 'Cold Brew'), (4, 'Kason', 'Espresso'), (5, 'Fiona', 'Mocha');

```

- [x] Kason
- [ ] Kason | Kason
- [ ] 查询结果为空
- [ ] Fiona | Kason | Simon

解析：子查询单独执行，得到喜欢 Espresso 的人 {Kason}；外层只看 coffee 是 Cold Brew 的行（id 3，Kason），Kason 在子查询结果里，所以结果是 Kason。

**代码题**：下面 SQL 执行后，最后一条查询的结果是什么？


**判断题**：
- ✅ 非相关子查询可以脱离外层查询单独执行 —— 它不引用外层的列，只需要执行一次
- ❌ IN 子查询都不能改写成 JOIN —— 课件：Many subqueries can be written as JOIN

### EXISTS 与相关子查询

**概念**：相关子查询（correlated subquery）引用了外层查询的列，外层每处理一行，子查询就要按这一行的值重新执行一次；EXISTS 只判断子查询有没有返回行，有就为真

**一句话**：课件例子"谁去了卖 Cold Brew 的咖啡店"：子查询里的 f.cafe = s.cafe 引用了外层的 f，所以是相关子查询；EXISTS 不关心子查询 SELECT 了什么，写 SELECT 1、SELECT *、SELECT NULL 都一样，只要有一行就是真；NOT EXISTS 不受 NULL 影响，比 NOT IN 安全。

**详细解释**：
Subquery Example 2 with EXISTS (correlated subquery)：Who goes to a cafe that serves 'Cold Brew'?
```sql
SELECT DISTINCT f.drinker
FROM frequents f
WHERE EXISTS (
  SELECT s.cafe
  FROM serves s
  WHERE s.coffee = 'Cold Brew' AND f.cafe = s.cafe);
```
FREQUENTS：Simon Cafe A；Ethan Cafe B；Kason Cafe C；Fiona Cafe C；Kason Cafe B。SERVES：Cafe A Mocha；Cafe B Cappuccino；Cafe C Cold Brew；Cafe B Cold Brew。
逐行判断：Simon 去的 Cafe A 不卖 Cold Brew；Ethan（Cafe B）、Kason（Cafe C）、Fiona（Cafe C）、Kason（Cafe B）都卖；DISTINCT 去掉重复的 Kason，结果：Ethan、Kason、Fiona。
相关子查询也可以是标量的：找出比同一种咖啡平均分高的评分，WHERE score > (SELECT AVG(r2.score) FROM rates r2 WHERE r2.coffee = r.coffee)。

**问题**：什么是相关子查询？IN 和 EXISTS 有什么区别？

**答案要点**：
1. 相关子查询引用外层查询的列，外层每一行都要重新执行一次
2. EXISTS 只看子查询是否返回了行，不关心返回的内容
3. IN 判断值是否在子查询结果集中，一般配非相关子查询
4. NOT IN 遇到子查询结果里有 NULL 会查不出任何行，NOT EXISTS 不会
5. 相关子查询数据量大时可能很慢，可以考虑改写成 JOIN

**对比**：
| | IN | EXISTS |
|---|---|---|
| 判断什么 | 值是否在结果集中 | 子查询是否有行 |
| 子查询类型 | 一般是非相关 | 一般是相关 |
| SELECT 列表 | 必须是要比较的列 | 写什么都一样 |
| 取反时遇到 NULL | NOT IN 结果为空 | NOT EXISTS 正常 |

**常见陷阱**：
- ❌ 以为 EXISTS (SELECT NULL FROM ...) 永远为假
- ✅ EXISTS 只看有没有行，返回的是 NULL 也算有一行，结果为真
- ❌ 相关子查询的条件里忘了引用外层的列（漏写 f.cafe = s.cafe）
- ✅ 子查询变成了非相关的，只要 serves 里有 Cold Brew，每个人都满足

**追问**：
- Q: IN 和 EXISTS 哪个快？
- A: 老说法是"子查询结果小用 IN、外层表小用 EXISTS"；MySQL 8.0 的优化器会把 IN 和 EXISTS 都转成半连接（semi-join）统一优化，多数情况下差别不大，以 EXPLAIN 为准

**代码题**：下面 SQL 执行后，最后一条查询的结果是什么？（每行用 | 隔开）

### FROM 子句中的子查询（派生表）

**概念**：写在 FROM 子句里的子查询会被当成一张临时表使用，MySQL 称为派生表（derived table），必须给它起别名

**一句话**：派生表让我们"先算出一个中间结果，再在上面查询"，比如课件里先查出卖 Cold Brew 的店，再和 frequents 连接；MySQL 要求派生表必须有别名，否则报 Every derived table must have its own alias；聚合函数不能直接嵌套（MAX(COUNT(*)) 会报错），"聚合的聚合"要先用派生表算出第一层。

**详细解释**：
Subqueries in FROM Clause：Treat the subquery in FROM clause as a temporary table；MUST be assigned an alias。
课件例子（Who goes to a cafe that serves 'Cold Brew'?）：
```sql
SELECT DISTINCT f.drinker
FROM frequents f,
  (SELECT s.cafe FROM serves s
    WHERE s.coffee = 'Cold Brew') s2
WHERE f.cafe = s2.cafe;
```
s2 = {Cafe C, Cafe B}，和 frequents 连接后得到 Ethan、Kason、Fiona、Kason 四行，DISTINCT 后三人。
聚合的聚合：
```sql
SELECT MAX(cnt)
FROM (SELECT drinker, COUNT(*) AS cnt FROM likes GROUP BY drinker) t;
```
派生表里的列名用别名（cnt）引用，外层查询只能看到派生表 SELECT 出来的列。
MySQL 8.0 还支持 WITH 子句（CTE），可以把派生表提到前面写，更好读，还能在同一条语句里引用多次。

**问题**：FROM 子句里的子查询有什么要求？什么时候必须用它？

**答案要点**：
1. FROM 中的子查询被当成临时表（派生表）
2. MySQL 中必须起别名
3. 外层通过别名引用派生表的列，计算列要起列别名
4. 聚合函数不能嵌套，"聚合的聚合"要借助派生表
5. 也可以用 CTE（WITH ... AS）改写，更清晰

**常见陷阱**：
- ❌ 写 SELECT MAX(COUNT(*)) FROM likes GROUP BY drinker 求"喜欢咖啡最多的人喜欢几种"
- ✅ 聚合函数不能嵌套，会报错，要先在派生表里 GROUP BY 算出 COUNT，再在外层求 MAX
- ❌ 派生表和外表连接后忘了 DISTINCT，以为每个人只出现一次
- ✅ 一个人匹配上派生表的多行就会出现多次（课件例子里 Kason 出现两次）

**追问**：
- Q: 派生表和视图有什么区别？
- A: 派生表只在当前这一条语句里存在；视图是保存在数据库里的查询定义，可以被很多语句反复使用

- ✅ MySQL 中 FROM 子句里的子查询必须起别名 —— 课件：MUST be assigned an alias，否则报 Every derived table must have its own alias
- ❌ 聚合函数可以直接嵌套使用，比如 MAX(COUNT(*)) —— 聚合函数不能嵌套，要先用派生表算出内层的聚合结果

### 视图（View）

**概念**：视图是一张虚拟表（virtual table），保存的是一条 SELECT 查询的定义而不是数据；每次查询视图时都会重新执行这条 SELECT，所以总能看到基表的最新数据

**一句话**：视图本身不存数据，基表变了视图马上跟着变；可以把复杂查询封装起来复用，也能只暴露部分行和列，提高安全性；对视图做 DML 实际改的是基表，但只有简单视图（没有聚合、DISTINCT、GROUP BY、UNION 等）才能更新，计算出来的列（比如 CONCAT 拼出的全名）也不能改。

**详细解释**：
A view is often seen as a virtual table；It is updated every time [it] is referred to；It displays data that you choose, but does not actually hold any data；Good for security since you can prevent showing extra data；DML operations just happen on the table: You can modify data on view level, and the source data will be updated as well。
课件例子：
```sql
CREATE VIEW hr_employees AS
SELECT CONCAT(first_name, ' ', last_name) AS full_name, salary
FROM employees
WHERE department = 'HR';
```
课件还用视图解决了"谁去了卖 Cold Brew 的店"：CREATE VIEW CB_COFFEE AS SELECT s.CAFE FROM SERVES s WHERE s.COFFEE = 'Cold Brew'；再 SELECT DISTINCT f.DRINKER FROM FREQUENTS f, CB_COFFEE c WHERE f.CAFE = c.CAFE。
可更新视图的条件：视图里的每一行能对应回基表的唯一一行；有聚合函数、DISTINCT、GROUP BY、HAVING、UNION、SELECT 列表里的子查询等都会让视图不可更新；hr_employees 的 salary 可以通过视图修改，full_name 不行。
WITH CHECK OPTION：禁止通过视图插入或修改出"不满足视图 WHERE 条件"的行。
MySQL 没有物化视图，视图的查询每次都会执行，不会因为建了视图就变快。

**问题**：什么是视图？视图有什么优点？能通过视图修改数据吗？

**答案要点**：
1. 视图是虚拟表，只保存查询定义，不存数据
2. 每次查询视图都重新执行定义，总是反映基表的最新数据
3. 优点：封装复杂查询、复用；只暴露需要的行和列，提高安全性
4. 简单视图可以 DML，修改的是基表；带聚合、DISTINCT、GROUP BY、UNION 的视图不能更新
5. MySQL 没有物化视图，视图本身不会提升查询性能

**对比**：
| | 视图 | 表 |
|---|---|---|
| 存什么 | 查询定义 | 实际数据 |
| 数据从哪来 | 每次查询时从基表现算 | 直接读取 |
| 修改数据 | 简单视图可以，改的是基表 | 可以 |
| 删除 | 不影响基表 | 数据一起删除 |

**常见陷阱**：
- ❌ 以为视图会保存创建那一刻的数据快照
- ✅ 视图不存数据，基表之后的修改都能通过视图看到
- ❌ 以为建了视图查询就会变快
- ✅ MySQL 的视图每次都执行原始查询，性能和直接写这条 SELECT 差不多

**追问**：
- Q: 为什么说视图有利于安全？
- A: 可以只把视图的权限授给用户，用户只能看到视图暴露的行和列（比如只看 HR 部门、看不到身份证号），而不能直接访问基表

**代码题**：下面 SQL 执行后，最后一条查询的结果是什么？

```sql
CREATE TABLE serves (id INT, cafe VARCHAR(10), coffee VARCHAR(20));
INSERT INTO serves VALUES (1, 'Cafe A', 'Mocha'), (2, 'Cafe B', 'Cappuccino'), (3, 'Cafe C', 'Cold Brew'), (4, 'Cafe B', 'Cold Brew');
CREATE VIEW cb_coffee AS SELECT cafe FROM serves WHERE coffee = 'Cold Brew';
INSERT INTO serves VALUES (5, 'Cafe A', 'Cold Brew');
SELECT COUNT(*) FROM cb_coffee;
```

- [x] 3
- [ ] 2
- [ ] 5
- [ ] 执行报错

解析：视图不保存数据，每次查询都会重新执行它的 SELECT；创建视图之后插入的 Cafe A Cold Brew 也会出现在视图里，所以是 3。

**代码题**：下面 SQL 执行后，最后一条查询的结果是什么？（每行用 | 隔开）

```sql
CREATE TABLE employees (id INT, first_name VARCHAR(20), last_name VARCHAR(20), department VARCHAR(10), salary INT);
INSERT INTO employees VALUES (1, 'Amy', 'Lee', 'HR', 5000), (2, 'Bob', 'Wu', 'IT', 7000), (3, 'Cat', 'Ng', 'HR', 6000);
CREATE VIEW hr_employees AS SELECT CONCAT(first_name, ' ', last_name) AS full_name, salary FROM employees WHERE department = 'HR';
UPDATE employees SET salary = 6500 WHERE id = 3;
SELECT full_name, salary FROM hr_employees ORDER BY full_name;
```

- [x] Amy Lee 5000 | Cat Ng 6500
- [ ] Amy Lee 5000 | Cat Ng 6000
- [ ] Amy Lee 5000 | Bob Wu 7000 | Cat Ng 6500
- [ ] 执行报错

解析：视图只暴露 HR 部门的全名和工资，看不到 Bob；基表里 Cat 的工资改成 6500 之后，查询视图时重新计算，看到的就是新值。

**判断题**：
- ✅ 视图本身不存储数据，每次查询视图都会重新执行它的定义 —— 课件：virtual table，does not actually hold any data，updated every time it is referred to
- ❌ 任何视图都可以通过 UPDATE 修改基表的数据 —— 只有简单视图可以更新，带聚合函数、DISTINCT、GROUP BY、UNION 的视图不行
