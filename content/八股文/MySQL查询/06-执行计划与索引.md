# 执行计划与索引

### 查询的执行过程与 EXPLAIN

**概念**：一条 SQL 在数据库里大致经过三步：解析器（Parser）检查语法并生成解析树，查询优化器（Query Optimizer）选出代价最低的执行计划，执行引擎按计划调用存储引擎读取数据；EXPLAIN 可以查看优化器选出的执行计划

**一句话**：SQL → 解析（语法检查、拆成 token、生成解析树）→ 优化（决定走哪个索引、多表按什么顺序连接）→ 执行（存储引擎真正读写数据）；在语句前面加 EXPLAIN 看执行计划，重点看 type（ALL 表示全表扫描）、key（实际用的索引）、rows（估计扫描行数）和 Extra（Using index、Using filesort、Using temporary）。

**详细解释**：
Query Execution：Step 1：Parser check query syntax；Break query to token（课件写成 intermediate files，实际是在内存里生成解析树）。Step 2：Query Optimizer creates the best possible execution plan based on current resource utilization。Step 3：DB engine → Run the query。
Execution Plan：EXPLAIN [Your_SQL]。
课件例子：film、inventory、rental、customer、address 五表 JOIN，WHERE f.title = 'Some Movie Title'；MySQL Workbench 的可视化执行计划显示：film 是 Full Table Scan（1000 rows，红色），inventory 走 idx_fk_film_id、rental 走 idx_fk_inventory_id（Non-Unique Key Lookup），customer、address 走 PRIMARY（Unique Key Lookup），各表之间用 nested loop（嵌套循环）连接，Query cost 8813.61。
MySQL 的架构：连接器 → 分析器（Parser）→ 优化器 → 执行器 → 存储引擎（InnoDB）；MySQL 8.0 删除了查询缓存。
优化器是基于代价（cost-based）的：根据表的统计信息估算每种方案要读多少行、多少页，选总代价最低的；统计信息不准时可能选错索引，可以 ANALYZE TABLE 更新统计信息。
EXPLAIN ANALYZE（MySQL 8.0.18+）会真正执行语句，并给出每一步实际的行数和耗时。

**问题**：一条 SQL 在 MySQL 中是怎么执行的？怎么看执行计划？

**答案要点**：
1. 解析器检查语法、生成解析树
2. 优化器根据统计信息估算代价，选出执行计划（用哪个索引、表的连接顺序）
3. 执行器按计划调用存储引擎（InnoDB）读写数据
4. EXPLAIN 查看执行计划：type、key、rows、Extra
5. type 为 ALL 表示全表扫描，key 为 NULL 表示没用上索引，通常是优化的重点

**对比**：
| type | 含义 | 例子 |
|---|---|---|
| ALL | 全表扫描 | 条件列上没有索引 |
| index | 扫描整棵索引树 | 只查索引列但没有过滤条件 |
| range | 索引范围扫描 | WHERE id BETWEEN 1 AND 100 |
| ref | 非唯一索引等值查找 | 课件里的 Non-Unique Key Lookup |
| eq_ref | 连接时用主键或唯一索引，每次最多一行 | 课件里的 Unique Key Lookup |
| const | 主键或唯一索引等值查找，最多一行 | WHERE id = 5 |

**常见陷阱**：
- ❌ 以为 EXPLAIN 会把查询执行一遍，可以用来看真实耗时
- ✅ 普通 EXPLAIN 只显示计划和估算值，不执行；要真实数据用 EXPLAIN ANALYZE
- ❌ 看到 key 列有值就认为查询已经很快
- ✅ 还要看 type 和 rows：type = index 也是扫描整棵索引树，rows 很大时照样慢

**追问**：
- Q: Extra 里出现 Using filesort 和 Using temporary 说明什么？
- A: Using filesort 表示排序没法利用索引的顺序，需要额外排序；Using temporary 表示用了临时表（常见于 GROUP BY、DISTINCT、UNION）；两者在大数据量时都很耗资源，通常要通过合适的索引消除

**判断题**：
- ✅ 查询优化器会估算不同方案的代价，选出执行计划，可以用 EXPLAIN 查看 —— 课件：Query Optimizer creates the best possible execution plan；Execution Plan：EXPLAIN [Your_SQL]
- ❌ EXPLAIN 结果中 type 为 ALL 表示查询用上了表上的所有索引 —— ALL 表示全表扫描，是最差的访问方式

### 索引与 B+ 树

**概念**：索引（Index）是为了加快数据检索而建立的数据结构，原理类似书的目录；MySQL InnoDB 的索引用 B+ 树实现，没有任何索引的表查数据只能全表扫描

**一句话**：没有索引时数据无序堆放，查一行要扫描整张表（O(n)）；B+ 树是多路平衡树，非叶子节点只存键用来导航，数据都在叶子节点，叶子节点之间用链表相连；一个节点能存很多键，树很矮（千万级数据一般 3~4 层），查一次只需要几次磁盘 IO，并且叶子链表让范围查询和排序很高效。

**详细解释**：
Indexes are used to speed up the retrieval of data from a database by providing quick access paths to the data；Operate similar to index in a book；Commonly implemented using a B+ Tree (some DBMS use B-Tree)。
If a table has no index at all, when new data is inserted, they are added wherever there is free space, and in no particular order；If you want to look up some data, you need to scan the entire table（Unordered Data Stored On Heap）。
Each clustered index composed of 3 main levels：Root Level、Intermediate Level、Leaf Page Level（Leaf pages are linked）；Leaf pages store index records and contain：Header（metadata）、Actual row data、Pointers。"3 层"只是常见情况，层数取决于数据量。
为什么用 B+ 树：
二叉搜索树 / 红黑树：每个节点只有两个分支，数据量大时树很高，每层一次磁盘 IO，太慢。
B 树：每个节点都存数据，节点能放的键变少，树更高；范围查询要在树里来回遍历。
B+ 树：非叶子节点只存键，扇出大、树矮；所有数据在叶子层，叶子用链表连接，范围查询找到起点后顺序往后读。
哈希索引：等值查找 O(1)，但不支持范围查询和排序。

**问题**：索引为什么能提高查询速度？MySQL 为什么用 B+ 树做索引？

**答案要点**：
1. 没有索引时只能全表扫描，O(n)；有索引时沿树查找，O(log n)
2. B+ 树是多路平衡树，非叶子节点只存键，扇出大，树很矮（一般 3~4 层）
3. 每层一次磁盘 IO，查一行只需要几次 IO
4. 叶子节点用链表相连，范围查询和按索引排序都很高效
5. 相比二叉树更矮，相比 B 树扇出更大且范围查询更好，相比哈希支持范围和排序

**对比**：
| 结构 | 等值查找 | 范围查询 | 树高 / 问题 |
|---|---|---|---|
| 二叉搜索树 | O(log n) | 要中序遍历 | 太高，可能退化成链表 |
| B 树 | 快 | 要在树里来回遍历 | 节点存数据，扇出小 |
| B+ 树 | 快 | 叶子链表顺序读 | 矮，InnoDB 采用 |
| 哈希 | O(1) | 不支持 | 不支持排序 |

**常见陷阱**：
- ❌ 认为 B+ 树就是"平衡二叉树"
- ✅ B+ 树是多路平衡树，一个节点（一页，InnoDB 默认 16KB）能放上百个键
- ❌ 认为数据量增长 1000 倍，查询要多走 1000 倍的步数
- ✅ B+ 树的高度随数据量对数增长，可能只多一层

**追问**：
- Q: InnoDB 一棵 3 层的 B+ 树大概能存多少行？
- A: 一页 16KB，假设主键是 BIGINT（8 字节）加 6 字节指针，一个非叶子页能放约 1170 个指针；叶子页每行按 1KB 算能放 16 行；3 层约 1170 × 1170 × 16 ≈ 2000 万行

**判断题**：
- ✅ InnoDB 的 B+ 树索引中，叶子节点之间用链表相连，适合范围查询 —— 课件：Leaf Page Level：Leaf pages are linked
- ❌ 没有任何索引的表，查找某一行只需要扫描一部分数据页 —— 课件：If you want to look up some data, you need to scan the entire table

### 聚集索引与非聚集索引

**概念**：聚集索引（Clustered Index）的叶子节点存放完整的行数据，表的数据按聚集键的顺序存储，一张表只能有一个；非聚集索引（Non-Clustered Index，InnoDB 叫二级索引）的叶子节点只存索引列和指向行的定位信息，一张表可以有多个

**一句话**：InnoDB 中主键就是聚集索引，表本身就是一棵按主键排序的 B+ 树；没有主键时用第一个 NOT NULL 的唯一索引，再没有就用隐藏的 row id，所以 InnoDB 的表一定有聚集索引；二级索引的叶子存的是主键值，通过二级索引查整行要先查到主键、再回聚集索引查一次（回表）。

**详细解释**：
Clustered Index is associated with PK, it determines the physical order of data in a table；Non-clustered Index is associated with Unique Keys, it stores data pointer to the data in the table（不只是唯一键，CREATE INDEX 建的普通索引也是非聚集索引）；Tables without a Clustered Index are called HEAP Tables（堆表是 SQL Server 的概念，InnoDB 的表一定有聚集索引）。
Clustered Indexes store actual row data in Leaf Pages and sort them based on the Key values of the column you choose；Non-Clustered Indexes will NOT store data in the Leaf Pages, instead they store pointers to the row they reference。
A clustered index organizes table data directly within its balanced B+Tree structure；The table rows are physically stored in the leaf pages of the index, so the logical order of the index matches the physical order of the data ⇒ rows are sorted by clustering key in ascending order；Because data can only be physically ordered once, a table can have only one clustered index。
Non-Clustered Index：Does not physically store data, so there can be many non-clustered index on a single table（课件说 up to 999，这是 SQL Server 的上限；InnoDB 一张表最多 64 个二级索引）。
InnoDB 二级索引的叶子存的是主键值而不是物理地址：数据页分裂、行移动时二级索引不用改；代价是回表要再查一次聚集索引。
主键建议用自增整数：新行总是追加在 B+ 树最右边，不会频繁页分裂；用 UUID 这类随机值做主键会导致插入位置随机、页分裂多，而且每个二级索引都要存一份较长的主键。

**问题**：聚集索引和非聚集索引有什么区别？InnoDB 的聚集索引是怎么选的？

**答案要点**：
1. 聚集索引的叶子节点存整行数据，表数据按聚集键排序存放
2. 一张表只能有一个聚集索引，可以有多个非聚集索引
3. InnoDB：有主键用主键；没有就用第一个 NOT NULL 的 UNIQUE 列；都没有就用隐藏的 row id
4. InnoDB 二级索引的叶子存索引列 + 主键值，查整行要回表
5. 主键最好用自增整数，避免页分裂，也让二级索引更小

**对比**：
| | 聚集索引 | 非聚集索引（二级索引） |
|---|---|---|
| 叶子节点存什么 | 整行数据 | 索引列 + 主键值 |
| 每张表数量 | 只能 1 个 | 多个（InnoDB 最多 64 个） |
| InnoDB 中对应 | 主键 | 唯一索引、普通索引 |
| 查整行 | 直接拿到 | 需要回表 |
| 数据顺序 | 决定行的物理顺序 | 不影响行的存放 |

**常见陷阱**：
- ❌ 认为 InnoDB 没定义主键的表是没有聚集索引的堆表
- ✅ InnoDB 会用第一个 NOT NULL 的唯一索引，或者自动生成隐藏的 row id 作为聚集索引
- ❌ 认为 InnoDB 二级索引的叶子存的是行的物理地址
- ✅ 存的是主键值，拿主键再到聚集索引里查整行

**追问**：
- Q: 为什么不推荐用 UUID 做 InnoDB 的主键？
- A: UUID 是随机的，新行会插到 B+ 树中间的随机位置，频繁页分裂、页利用率低；而且 UUID 比整数长，每个二级索引的叶子都要存一份主键，索引变大

**判断题**：
- ✅ 一张表只能有一个聚集索引 —— 课件：Because data can only be physically ordered once, a table can have only one clustered index
- ❌ InnoDB 二级索引的叶子节点存储完整的行数据 —— 只有聚集索引的叶子存整行，二级索引的叶子存索引列和主键值

### 回表与覆盖索引

**概念**：通过二级索引找到主键后，再到聚集索引里取整行数据的过程叫回表；如果查询需要的列都已经包含在二级索引里，就不需要回表，这种情况叫覆盖索引（covering index）

**一句话**：按主键查（WHERE id = 5）直接走聚集索引，一次拿到整行；按二级索引列查时先在二级索引里找到主键，再回聚集索引取整行，要走两棵 B+ 树；如果只 SELECT 二级索引里已有的列（加上主键），就不用回表，EXPLAIN 的 Extra 显示 Using index；这也是不要随手写 SELECT * 的原因之一。

**详细解释**：
Query situation：The SQL uses the clustered index field (e.g, where ID = XXX)：Clustered index is used directly；The SQL uses the non-clustered index fields：DB navigates to the non-clustered index on the given field；Finds the matching entry and retrieves the PK；Use the PK to look up the full row on clustered index。
课件例子：
```sql
create table zookeeper(
    id int auto_increment primary key,
    email varchar(20) unique,
    name varchar(20)
);
create index indexname on zookeeper(name);

SELECT * FROM zookeeper WHERE id = 5;
SELECT email FROM zookeeper WHERE email = 'abc@example.com';
```
这张表有 3 个索引：id 的聚集索引、email 的唯一索引（UNIQUE 自动创建）、name 的普通索引。
第一条按主键查，直接走聚集索引；第二条走 email 的二级索引，而且只要 email 这一列，二级索引里就有，不需要回表，是覆盖索引。
课件的 Data Retrieval 图：找 last_name = Semorad，先在 last_name 的非聚集索引里一路找到叶子，拿到 id，再到 id 的聚集索引里找到数据页。
联合索引可以把常用的查询列都放进去，让更多查询变成覆盖索引，比如 INDEX(name, email) 能覆盖 SELECT email FROM zookeeper WHERE name = ?。

**问题**：什么是回表？什么是覆盖索引？

**答案要点**：
1. 按主键查询直接走聚集索引，拿到整行
2. 按二级索引列查询：先在二级索引找到主键，再到聚集索引取整行，这一步叫回表
3. 查询的列全部在二级索引中（包括主键）时不需要回表，叫覆盖索引
4. 覆盖索引在 EXPLAIN 的 Extra 中显示 Using index
5. 只查需要的列、合理设计联合索引，可以减少回表

**对比**：
| 查询（zookeeper） | 用到的索引 | 是否回表 |
|---|---|---|
| SELECT * WHERE id = 5 | 聚集索引 | 不需要 |
| SELECT email WHERE email = ? | email 唯一索引 | 不需要（覆盖索引） |
| SELECT id, name WHERE name = ? | name 普通索引 | 不需要（二级索引里有主键） |
| SELECT * WHERE name = ? | name 普通索引 | 需要 |

**常见陷阱**：
- ❌ 认为只要走了索引，就不会再访问表数据
- ✅ 走二级索引时，SELECT 了索引里没有的列就要回表，匹配行多时回表次数也多
- ❌ 习惯写 SELECT *
- ✅ 本来能用覆盖索引的查询被迫回表，还会读取、传输不需要的列

**追问**：
- Q: SELECT id, name FROM zookeeper WHERE name = 'Amy' 需要回表吗？
- A: 不需要；InnoDB 的二级索引叶子里存着索引列 name 和主键 id，要的两列都在，属于覆盖索引

**判断题**：
- ✅ 查询需要的列都包含在二级索引中时，不需要回表，这叫覆盖索引 —— 课件例子 SELECT email FROM zookeeper WHERE email = 'abc@example.com' 只需要 email 的二级索引
- ❌ 只要查询条件用的是二级索引，就一定需要回表 —— 要的列都在二级索引里（覆盖索引）时不需要回表

### 键（Key）与索引（Index）

**概念**：键是逻辑上的约束，用来保证数据的唯一性和引用关系（主键、唯一键、外键）；索引是物理上的数据结构，用来加快查找；数据库通常借助索引来实现主键和唯一约束，但索引不一定是键

**一句话**：课件说 Keys ≠ Indexes：主键、唯一键在 MySQL 中会自动建对应的索引来检查唯一性，外键列 InnoDB 也会自动建索引；但 CREATE INDEX 建的普通索引只是为了加速，允许重复值，不保证唯一，也不表示任何约束；想要唯一就建 UNIQUE 约束或唯一索引。

**详细解释**：
课件：Keys ≠ Indexes。
键（约束）：PRIMARY KEY（唯一且非空）、UNIQUE（唯一，允许 NULL）、FOREIGN KEY（引用另一张表的键）。
索引（结构）：主键索引（InnoDB 中就是聚集索引）、唯一索引、普通索引、联合索引、全文索引等。
关系：MySQL 定义 PRIMARY KEY、UNIQUE 时会自动创建同名的唯一索引来执行检查；InnoDB 要求外键列上有索引，没有会自动创建。
课件 zookeeper 例子：email varchar(20) unique 是唯一约束，会自动带一个唯一索引；create index indexname on zookeeper(name) 是普通索引，name 可以重复。
建唯一索引时如果表里已有重复值，CREATE UNIQUE INDEX 会失败。

**问题**：键和索引有什么区别和联系？

**答案要点**：
1. 键是逻辑约束：主键、唯一键、外键，保证数据正确
2. 索引是物理结构：B+ 树，加快查找
3. MySQL 用唯一索引来实现主键和唯一约束，外键列会自动建索引
4. 普通索引允许重复值，只用于加速，不是键
5. 唯一索引会拒绝重复值，作用和 UNIQUE 约束相同

**对比**：
| | PRIMARY KEY | UNIQUE | 普通 INDEX |
|---|---|---|---|
| 是否约束 | 是 | 是 | 否 |
| 允许重复 | 否 | 否 | 是 |
| 允许 NULL | 否 | 是（可以多个） | 是 |
| 每表数量 | 1 个 | 多个 | 多个 |
| 背后的索引 | 聚集索引（InnoDB） | 唯一二级索引 | 普通二级索引 |

**常见陷阱**：
- ❌ 以为给列建了普通索引，就能防止重复数据
- ✅ 普通索引允许重复，要用 UNIQUE 约束或 CREATE UNIQUE INDEX
- ❌ 以为主键和"主键上的索引"是两个需要分别创建的东西
- ✅ 定义 PRIMARY KEY 时数据库会自动建好对应的索引

**追问**：
- Q: 外键列需要自己建索引吗？
- A: InnoDB 要求外键列上有索引，没有时会自动创建；这样删除或更新父表记录时检查子表，不用全表扫描

**代码题**：下面 SQL 执行后，最后一条查询的结果是什么？

```sql
CREATE TABLE zookeeper (id INT PRIMARY KEY, email VARCHAR(20), name VARCHAR(20));
CREATE INDEX idx_name ON zookeeper(name);
INSERT INTO zookeeper VALUES (1, 'a@x.com', 'Amy'), (2, 'b@x.com', 'Amy');
SELECT COUNT(*) FROM zookeeper WHERE name = 'Amy';
```

- [x] 2
- [ ] 1
- [ ] 0
- [ ] 执行报错

解析：idx_name 是普通索引，只用来加快按 name 查找，不限制重复值，两个 Amy 都能插入。

- [x] 执行报错
- [ ] 查询结果为空

解析：唯一索引会拒绝重复值，第二条 INSERT 的 email 和第一条相同，执行报错；这就是 UNIQUE 约束在数据库内部的实现方式。

**判断题**：
- ✅ 键是逻辑约束，索引是加快查找的物理结构，普通索引允许重复值 —— 课件：Keys ≠ Indexes
- ❌ 用 CREATE INDEX 给某列建普通索引后，这一列就不能再出现重复值 —— 只有唯一索引（UNIQUE）才限制重复，普通索引只负责加速

### 索引的代价与失效

**概念**：索引能加快查询，但不是越多越好：每个索引都要占空间，并且在每次写入时同步维护；有些查询写法或数据分布还会让索引用不上（索引失效），优化器可能宁愿全表扫描

**一句话**：面试题"索引一定能提高性能吗"的答案是不一定：INSERT / UPDATE / DELETE 都要同时维护所有相关索引，写变慢、占空间；表很小、区分度低（比如性别）、要返回大部分行时，走索引加回表反而比全表扫描慢；对索引列用函数或计算、LIKE 以 % 开头、隐式类型转换、联合索引不满足最左前缀，都会让索引失效。

**详细解释**：
Interviews Questions：How does Index improve the performance? Hint: Index lookup vs. Table Scan；Will Index always improve the performance? Hint: Index adds maintenance overhead。
Index lookup vs Table Scan：全表扫描逐行检查，O(n)；索引查找沿 B+ 树从根到叶子，O(log n)，再顺着叶子链表做范围扫描。
维护开销：插入一行要在每个索引的 B+ 树里插入一项，可能引起页分裂；更新索引列要删旧项、插新项；删除也要同步。
常见的索引失效：
WHERE YEAR(created_at) = 2024：对索引列用函数，改成 created_at >= '2024-01-01' AND created_at < '2025-01-01'。
WHERE name LIKE '%abc'：以通配符开头，B+ 树无法定位起点；LIKE 'abc%' 可以用索引。
WHERE phone = 13800000000：phone 是字符串列却和数字比较，会对列做类型转换。
联合索引 INDEX(a, b, c)：WHERE b = 1 不满足最左前缀，用不上；WHERE a = 1 AND c = 1 只能用到 a。
OR 连接的条件里有一个列没有索引，可能整体放弃索引。
建索引的原则：WHERE、JOIN、ORDER BY、GROUP BY 常用的列；区分度高的列；联合索引把等值条件、区分度高的列放前面；避免冗余索引（有了 (a, b) 就不需要单独的 (a)）。

**问题**：索引一定能提高性能吗？哪些情况下索引会失效？

**答案要点**：
1. 不一定：索引要占空间，每次写操作都要维护，写多的表索引太多会拖慢写入
2. 小表、区分度低的列、要返回大部分行的查询，全表扫描可能更快
3. 对索引列使用函数或表达式会导致索引失效
4. LIKE 以 % 开头、隐式类型转换也会让索引失效
5. 联合索引要满足最左前缀原则

**对比**：
| 写法 | 能否用 INDEX(created_at) / INDEX(name) |
|---|---|
| WHERE YEAR(created_at) = 2024 | 不能（列上用了函数） |
| WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01' | 能（范围扫描） |
| WHERE name LIKE 'Am%' | 能 |
| WHERE name LIKE '%my' | 不能 |

**常见陷阱**：
- ❌ 给表的每一列都建上索引，认为查询会全面变快
- ✅ 写入要维护所有索引，变慢、占空间，优化器也可能选错；只给常用查询条件建索引
- ❌ 给性别、状态这种只有几个取值的列单独建索引
- ✅ 区分度太低，走索引还要大量回表，优化器多半还是全表扫描

**追问**：
- Q: 联合索引 INDEX(a, b) 对 WHERE b = 1 AND a = 2 有用吗？
- A: 有用；最左前缀看的是条件里有没有 a，不是书写顺序，优化器会自动调整，所以 a、b 都能用上

**判断题**：
- ✅ 索引会降低 INSERT、UPDATE、DELETE 的速度，因为写入时要同时维护索引 —— 课件 Hint：Index adds maintenance overhead
- ❌ 只要建了索引，查询就一定比全表扫描快 —— 小表、低区分度、返回大量行或索引失效时，全表扫描可能更快

### 查询优化

**概念**：从数据库角度提升应用性能，通常从看执行计划、建合适的索引、优化 JOIN、尽早过滤和只取需要的列、合理的表设计几个方面入手

**一句话**：先用 EXPLAIN 找到慢在哪（全表扫描、filesort、扫描行数太多）；给 WHERE、JOIN、ORDER BY 用到的列建合适的索引；大表 JOIN 要保证连接列有索引、先过滤再连接；尽早用 WHERE 减少行数，不写 SELECT * 只取需要的列；表结构按范式设计，读多写少的场景再适当反规范化。

**详细解释**：
Question: How to improve the performance of your application? (Database version)
Execution Plan：Look into execution plan to analyze the performance of your query。
Index：Ensure the tables are properly indexed。
Optimize JOINs：Try to avoid using JOIN statements on large tables if possible。
Filter early: avoid SELECT *, only get the needed information（其实是两件事：尽早用 WHERE 减少参与后续计算的行；只取需要的列，减少 IO 和网络传输，还可能用上覆盖索引）。
Database Design：ensure the data is normalized（上一份课件也讲了，读多写少时会反规范化，用少量冗余换更少的 JOIN）。
补充：开启慢查询日志（slow_query_log）找出慢 SQL；深分页 LIMIT 100000, 10 改成按上一页最后的 id 继续查；批量插入代替逐条插入；避免在循环里一条条查询（N+1 问题）；能用 UNION ALL 就不用 UNION。

**问题**：从数据库的角度，怎么提升应用的性能？

**答案要点**：
1. 用慢查询日志和 EXPLAIN 找出慢 SQL，分析执行计划
2. 给常用的查询条件、连接列、排序列建合适的索引，避免索引失效
3. 优化 JOIN：连接列有索引，先过滤再连接，避免大表之间不必要的 JOIN
4. 尽早过滤，只查需要的列，不写 SELECT *
5. 表结构合理（规范化，必要时反规范化），配合分页优化、批量操作、缓存

**对比**：
| 方法 | 解决的问题 |
|---|---|
| EXPLAIN | 定位全表扫描、错误的索引、额外排序 |
| 索引 | 把全表扫描变成索引查找 |
| 优化 JOIN | 减少参与连接的行数和扫描次数 |
| 只查需要的列 | 减少 IO、网络传输，争取覆盖索引 |
| 规范化 / 反规范化 | 在写入一致性和读取速度之间取舍 |

**常见陷阱**：
- ❌ 一遇到慢查询就先加索引
- ✅ 先 EXPLAIN 看原因：可能是索引失效、写法问题或者返回的数据太多，加索引不一定有用
- ❌ 分页一直用 LIMIT 很大的偏移量
- ✅ MySQL 要先扫过前面所有的行再丢掉，偏移量越大越慢，改成按上一页最后一个 id 继续查

**追问**：
- Q: 为什么说"Filter early"？
- A: WHERE 越早把不需要的行过滤掉，后面的 JOIN、GROUP BY、ORDER BY 要处理的数据就越少；能在 WHERE 里写的条件不要放到 HAVING 里

**判断题**：
- ✅ 只查询需要的列而不是 SELECT *，可以减少读取和传输的数据量，还可能用上覆盖索引 —— 课件：Filter early: avoid SELECT *, only get the needed information
- ❌ 为了让所有查询都变快，应该给表的每一列都建索引 —— 索引有维护开销，太多会拖慢写入，只应该给常用的查询条件建索引
