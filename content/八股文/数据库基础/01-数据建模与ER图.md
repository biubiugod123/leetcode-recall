# 数据建模与ER图

### 数据建模与关系数据库术语

**概念**：数据建模（Data Modeling）是分析业务需求、设计出数据库或数据仓库蓝图的过程，是软件开发生命周期（SDLC）中的一个阶段

**一句话**：关系数据库里 Row 也叫 Tuple / Record，Column 也叫 Attribute / Field，Table 也叫 Relation，查询结果或视图是 Derived relvar；建模时要识别实体（Entity）、属性（Attribute）、域（Domain，属性的合法取值范围）和实体之间的关系（Relationship）；数据模型还会影响用户界面能展示和录入什么。

**详细解释**：
Data Modeling is the process of analyzing business requirements, designing and creating physical instance (a plan or a blueprint) for the database or data warehouse；It is a stage in SDLC；It also impacts the user interface。
术语对照：
Row ↔ Tuple or record：表示一个条目的一组数据
Column ↔ Attribute or Field：元组里有名字的元素，比如 Address、Date of birth
Table ↔ Relation or Base relvar：共享相同属性的一组元组
View or Result set ↔ Derived relvar：RDBMS 对查询返回的数据
建模术语：Entity（可以独立存在或被唯一标识的事物）、Attribute（列名）、Domain（属性合法取值的集合，比如 NOT NULL）、Relationship（实体如何关联）、Degree（关系里有几个实体）、Cardinality（参与程度）。
为 MySQL 做数据建模，包括规范化、画 ERD、建表、定义关系、设置主键外键、规划索引。

**问题**：什么是数据建模？关系数据库里的 Tuple、Attribute、Relation 分别对应什么？

**答案要点**：
1. 数据建模：分析业务需求，设计数据库的蓝图，是 SDLC 的一个阶段
2. Row = Tuple / Record，Column = Attribute / Field，Table = Relation
3. 视图或查询结果集 = Derived relvar
4. Entity 是可被唯一标识的事物，Attribute 是它的属性，Domain 是属性的合法取值范围
5. 建模结果包括 ERD、表结构、主外键和索引规划

**对比**：
| SQL 术语 | 关系数据库术语 | 含义 |
|---|---|---|
| Row | Tuple / Record | 一个条目 |
| Column | Attribute / Field | 一个字段 |
| Table | Relation | 一组具有相同属性的元组 |
| View / Result set | Derived relvar | 查询得到的元组集合 |

**常见陷阱**：
- ❌ 把"关系型数据库"里的"关系"理解成表与表之间的外键关系
- ✅ 这里的 Relation 指的就是"表"（元组的集合），表之间的联系叫 Relationship

**追问**：
- Q: Domain 和数据类型有什么区别？
- A: 数据类型是存储格式（INT、VARCHAR）；Domain 是业务上的合法取值集合，比如状态只能是 Active / Inactive，通常用类型 + CHECK / NOT NULL 等约束来实现

**判断题**：
- ✅ 在关系数据库术语中，Table 也被称为 Relation —— Row 对应 Tuple，Column 对应 Attribute
- ❌ Domain 指的是一张表里所有列的名字 —— Domain 是某个属性合法取值的集合

### 数据建模中的键

**概念**：键（Key）是用来唯一标识表中一行的一个或多个属性；常见的有超键、候选键、主键、备选键、复合键、外键、代理键和自然键

**一句话**：超键是能唯一标识一行的属性组合；候选键是最小的超键；从候选键里选一个做主键（每表一个），其余的是备选键；由多列组成的键是复合键；外键引用另一张表的主键；代理键是自增 ID 这类没有业务含义的键，自然键是 SSN、订单号这类有业务含义的键。

**详细解释**：
Super key：One or multiple attributes that can uniquely identify a row。
Unique key / Candidate key：Minimal super key；No proper subset of candidate key can uniquely identify a row。
Primary key：Selected candidate key；One per table；Usually ID column。
Alternate key：All candidate keys that are not primary key。
Composite key：Superkey with two or more attributes。
Foreign key：A column which is known as Primary key in the other table。
Surrogate Key：Unique identifier；Does NOT carry any meaning about the data it represent；Often auto-generated by the DBMS（比如 AddressID）。
Natural Key：formed of real-world data；Carries meaning（比如 SSN、order_number）。
课件例子：学生表里 StudID、Roll No、Email 都是候选键，选 StudID 当主键，其余是备选键；扑克牌表里 Suit 或 Value 单独都不唯一，(Suit, Value) 组合起来才唯一，是复合键。

**问题**：超键、候选键、主键有什么区别？代理键和自然键怎么选？

**答案要点**：
1. 超键：能唯一标识行的任意属性组合
2. 候选键：最小的超键，去掉任何一列就不唯一了
3. 主键：选中的那个候选键，每表一个；没选中的是备选键
4. 复合键由多列组成；外键引用另一张表的主键
5. 代理键无业务含义、稳定，常用自增 ID；自然键有业务含义，但业务变化时可能要改

**对比**：
| 键 | 特点 | 例子 |
|---|---|---|
| Super key | 能唯一标识行，可以有多余的列 | (StudID, Email) |
| Candidate key | 最小的超键 | StudID、Email、Roll No |
| Primary key | 选中的候选键，每表一个 | StudID |
| Alternate key | 没被选中的候选键 | Email、Roll No |
| Composite key | 多列组成 | (Suit, Value) |
| Surrogate key | 无业务含义，自动生成 | AddressID |
| Natural key | 有业务含义 | SSN |

**常见陷阱**：
- ❌ 认为所有超键都是候选键
- ✅ 候选键必须是最小的：(StudID, Email) 是超键，但去掉 Email 仍唯一，所以不是候选键
- ❌ 用会变化的业务字段（手机号、邮箱）当主键
- ✅ 主键最好稳定不变，常用代理键，业务字段另外加唯一约束

**追问**：
- Q: 为什么很多表用自增 ID 而不是身份证号这类自然键当主键？
- A: 代理键短、稳定、不暴露隐私，外键引用也方便；自然键可能变化、可能很长，修改时要连带更新所有外键

**代码题**：下面 SQL 执行后，最后一条查询的结果是什么？

```sql
CREATE TABLE cards (suit VARCHAR(10), card_value VARCHAR(10), played INT, PRIMARY KEY (suit, card_value));
INSERT INTO cards VALUES ('Hearts', 'Ace', 5), ('Diamonds', 'Ace', 2), ('Hearts', 'Jack', 3);
SELECT COUNT(*) FROM cards;
```

- [x] 3
- [ ] 2
- [ ] 1
- [ ] 执行报错

解析：复合主键要求 (suit, card_value) 的组合唯一；三行的组合都不同，虽然 suit 或 card_value 单独有重复，也能全部插入。

**代码题**：下面 SQL 执行结果是什么？

```sql
CREATE TABLE cards (suit VARCHAR(10), card_value VARCHAR(10), played INT, PRIMARY KEY (suit, card_value));
INSERT INTO cards VALUES ('Hearts', 'Ace', 5);
INSERT INTO cards VALUES ('Hearts', 'Ace', 7);
SELECT COUNT(*) FROM cards;
```

- [ ] 2
- [ ] 1
- [x] 执行报错
- [ ] 查询结果为空

解析：第二条 INSERT 的 (suit, card_value) 和第一条完全相同，违反了复合主键的唯一性，执行报错。

**判断题**：
- ✅ 候选键是最小的超键 —— 它的任何真子集都不能唯一标识一行
- ❌ 代理键（Surrogate Key）携带了业务含义 —— 代理键没有业务含义，有业务含义的是自然键

### 基数与度

**概念**：基数（Cardinality）描述一个实体在关系中参与的次数，比如 1:1、1:N、N:M；度（Degree）描述一个关系涉及几个实体

**一句话**：1:1 是双方各对应一个（学生和座位），1:N 是一方对应多个（老师和课程），N:M 是双方都可以对应多个（学生和课程）；度通常是 2（二元关系），也有一元（自己关联自己，比如员工和他的经理）、三元和 N 元；基数和度是两个不同的概念。

**详细解释**：
Cardinality is the number of times the entity participates in the relationship：
One-to-One (1:1)：One element in EntityA may link to one element in EntityB and vice versa
One-to-Many (1:N)：One element in EntityA may link to many elements in EntityB but one element in EntityB may only link to one element in EntityA
Many-to-One (N:1)：Reverse A and B in 1:N
Many-to-Many (N:M)：One element in Entity A may link to any number of elements in Entity B and vice versa
Degree is the number of entities involved in the relationship and it is usually 2 (binary relationship) however Unary and higher degree relationships can exist。
课件例子：Student manages Student（unary，degree 1）；Customer has Account（binary，1:n）；Employee works in Department at Location（ternary，degree 3）；E1~E5 通过 R 关联（N-ary）。
建表方式：1:N 在"多"的一方放外键；N:M 需要中间表；1:1 可以在任意一方放唯一外键，或者合并成一张表。

**问题**：什么是基数和度？1:1、1:N、N:M 在建表时分别怎么处理？

**答案要点**：
1. 基数：实体在关系中参与多少次（1:1、1:N、N:1、N:M）
2. 度：关系涉及几个实体，通常是 2，也有一元、三元、N 元
3. 1:N：在"多"的一方加外键
4. N:M：建中间表，两个外键组成复合主键
5. 1:1：在一方加唯一外键，或者合并成一张表

**对比**：
| | 基数 Cardinality | 度 Degree |
|---|---|---|
| 描述 | 参与的次数 | 参与的实体数量 |
| 取值 | 1:1、1:N、N:1、N:M | 1（一元）、2（二元）、3（三元）、N |
| 例子 | 一个老师教多门课 | Employee、Department、Location 三元关系 |

**常见陷阱**：
- ❌ 把"二元关系"理解成"一对多"
- ✅ 二元说的是度（两个实体参与），一对多说的是基数，两者不是一回事
- ❌ 在 1:N 关系里把外键放在"一"的那一方
- ✅ 外键放在"多"的一方，比如订单表里放 customer_id

**追问**：
- Q: 员工表里每个员工有一个经理，经理也是员工，这是什么关系？怎么建表？
- A: 一元（unary）的 1:N 关系；在员工表里加一个 manager_id 外键，引用同一张表的主键（自引用）

**判断题**：
- ✅ 一个关系的度（Degree）指的是参与这个关系的实体数量 —— 最常见的是 2，即二元关系
- ❌ 基数和度描述的是同一件事 —— 基数是参与次数（1:1、1:N），度是参与的实体个数

### ER 图、Crow's Foot 与转换成表

**概念**：ER 图（Entity Relationship Diagram）用来设计数据库的蓝图，画出实体、属性和它们之间的关系；Crow's Foot（鸟爪）表示法用连接线两端的符号表示基数

**一句话**：Crow's Foot 中竖线 ┼ 表示"一"，鸟爪 < 表示"多"，圆圈 ○ 表示"可以没有"：┼┼ 是有且只有一个，┼< 是一个或多个，○┼ 是零个或一个，○< 是零个或多个；把 ER 图转成表时，实体变成表，单值属性变成列，派生属性忽略或做成计算列，多值属性单独建表，多对多关系用中间表拆开，键属性变成主键或唯一键。

**详细解释**：
ER-Diagram：Entity Relationship Diagram；Used to create or design a blueprint of the Database or Data Warehouse；Design Entities, attributes and show relationships。
Crow's Foot Notation：Connection symbols display relationships；Entity and Attributes in table-like format。
符号：──┼┼── One–Mandatory；──┼<── Many–Mandatory；──○┼── One–Optional；──○<── Many–Optional。靠近实体的符号表示最多几个，外侧的符号表示最少几个。
例子：STUDENT fills SEAT（1:1）；INSTRUCTOR teaches COURSE（1:M）；STUDENT takes COURSE（M:M）；PROFESSOR teaches SECTION（1:M，可选）。
Convert ERD to Tables：Each entity type becomes a table；Each single-valued attribute becomes a column；Derived attributes are ignored / computed column；Multi-valued attributes are represented by a separate table；Use Conjunction Table to break up the Many-to-Many relationship；The key attribute of the entity type becomes the primary key or unique key of the table。

**问题**：怎么把 ER 图转换成数据库表？多对多关系怎么处理？

**答案要点**：
1. 每个实体变成一张表，单值属性变成列
2. 派生属性（比如年龄）不存，或者做成计算列
3. 多值属性（比如多个电话）单独建一张表
4. 多对多关系用中间表（关联表）拆成两个一对多
5. 实体的键属性变成主键或唯一键；Crow's Foot 用竖线、鸟爪、圆圈表示一、多、可选

**对比**：
| 符号 | 含义 |
|---|---|
| ──┼┼── | 有且只有一个（One – Mandatory） |
| ──┼< | 一个或多个（Many – Mandatory） |
| ──○┼ | 零个或一个（One – Optional） |
| ──○< | 零个或多个（Many – Optional） |

**常见陷阱**：
- ❌ 多对多关系直接在一张表里放另一张表的多个 id（比如 course_ids = '1,2,3'）
- ✅ 违反 1NF，查询和维护都困难，应该建中间表

**追问**：
- Q: 中间表的主键一般怎么设计？
- A: 用两个外键组成复合主键，保证同一对关系不会重复；也可以另加一个代理主键，再给两个外键加联合唯一约束

**代码题**：下面 SQL 执行后，最后一条查询的结果是什么？（每行用 | 隔开）

```sql
CREATE TABLE student (id INT PRIMARY KEY, name VARCHAR(20));
CREATE TABLE course (id INT PRIMARY KEY, title VARCHAR(20));
CREATE TABLE student_course (student_id INT, course_id INT, PRIMARY KEY (student_id, course_id));
INSERT INTO student VALUES (1, 'Amy'), (2, 'Ben');
INSERT INTO course VALUES (10, 'DB'), (20, 'Java');
INSERT INTO student_course VALUES (1, 10), (1, 20), (2, 10);
SELECT s.name, COUNT(*) FROM student s JOIN student_course sc ON s.id = sc.student_id GROUP BY s.name ORDER BY s.name;
```

- [x] Amy 2 | Ben 1
- [ ] Amy 1 | Ben 1
- [ ] Amy 2 | Ben 2
- [ ] Amy 3

解析：学生和课程是多对多，用中间表 student_course 记录"谁选了哪门课"；Amy 选了 2 门，Ben 选了 1 门。

**判断题**：
- ✅ 多对多关系在建表时需要一张中间表 —— 中间表分别引用两边的主键
- ❌ 派生属性（比如由出生日期算出的年龄）必须作为普通列存进表里 —— 派生属性一般不存，查询时计算，或做成计算列
