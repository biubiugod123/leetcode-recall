# 范式与数据完整性

### 冗余与三种异常

**概念**：冗余（Redundancy）是同样的值在多条记录或多张表里不必要地重复；冗余会导致异常（Anomaly），即修改数据时出现的副作用，分为更新异常、插入异常和删除异常

**一句话**：更新异常：同一信息存在多行，只改了一部分就出现矛盾；插入异常：某些事实根本录不进去（新老师还没分配课程，课程号又是键的一部分）；删除异常：删一条事实时连带删掉了另一条完全不同的事实（删掉老师唯一的课，老师的信息也没了）；规范化就是为了消除冗余和这些异常。

**详细解释**：
Redundancy：Values repeated unnecessarily in multiple records or fields within one or more tables；课件例子：病人表里每行都重复了医生 "01 / Dr Hyde / 03"。
Anomaly：When an attempt is made to modify (update, insert into, or delete from) a relation, the following undesirable side-effects may arise in relations that have not been sufficiently normalized；Anomaly is the issue that may occur because of redundancy；Types: Update, Insertion and Deletion。
Update Anomaly：The same information can be expressed on multiple rows; therefore updates may result in logical inconsistencies（员工 519 有两行，地址却不一样）。
Insertion Anomaly：There are circumstances in which certain facts cannot be recorded at all（新老师 Dr. Newsome 没有课程，录不进"老师和课程"表）。
Deletion Anomaly：deletion of data representing certain facts necessitates deletion of data representing completely different facts（删掉 Dr. Giddens 的唯一一门课，老师的信息也被删了）。
解决办法：把不同的事实拆到不同的表里，比如医生表、老师表、授课表。

**问题**：什么是数据冗余？会导致哪些异常？

**答案要点**：
1. 冗余：同样的数据在多处不必要地重复
2. 更新异常：只改了部分重复数据，导致前后矛盾
3. 插入异常：缺少某部分信息时，另一部分事实无法录入
4. 删除异常：删除一个事实时连带丢失了另一个事实
5. 通过规范化把不同的事实拆到不同的表来消除

**对比**：
| 异常 | 现象 | 课件例子 |
|---|---|---|
| 更新异常 | 数据前后矛盾 | 员工 519 有两个不同的地址 |
| 插入异常 | 事实无法录入 | 没有课程的新老师录不进去 |
| 删除异常 | 连带丢失其他事实 | 删掉唯一的课，老师的信息也没了 |

**常见陷阱**：
- ❌ 认为冗余只是浪费存储空间
- ✅ 更严重的是会导致数据不一致和各种异常

**追问**：
- Q: 怎么改造"病人-医生"那张表消除冗余？
- A: 拆成病人表和医生表，医生的姓名、房间号只在医生表存一份，病人表里只保留 doctor_id 外键

**判断题**：
- ✅ 数据异常（anomaly）通常是由冗余引起的 —— 同样的信息存了多份，修改时容易不一致
- ❌ 插入异常是指同一条数据被插入了两次 —— 插入异常是因为缺少其他信息，某些事实根本无法录入

### 函数依赖与 1NF、2NF、3NF

**概念**：函数依赖（Functional Dependency）描述表中属性之间的决定关系；按依赖类型逐步拆表就是规范化：1NF 要求原子值，2NF 消除部分依赖，3NF 消除传递依赖

**一句话**：主键和候选键里的属性是主属性，其余是非主属性；完全依赖是依赖整个主键，部分依赖是只依赖复合主键的一部分，传递依赖是通过另一个非主属性间接依赖主键（A → B → C）；1NF 每个单元格只有一个值、每行唯一，2NF 在 1NF 基础上所有非主属性完全依赖主键，3NF 在 2NF 基础上非主属性不传递依赖主键。

**详细解释**：
Functional Dependencies：how different attributes relate in a table；focus on individual tables；Primary Key & Candidate Keys = Prime Attributes；Attributes that aren't keys = Non-Prime Attributes。
Types：Full（depends on all prime attributes fully）；Partial（depends on some prime attributes）；Transitive（depends on an attribute that depends on a prime attribute）。
1NF：Each table cell should contain a single value；Each record needs to be unique。
2NF：Meets all of 1NF；all non-prime attributes are fully dependent on a prime attribute。
3NF：Meets 1NF and 2NF；Every non-prime attribute is non-transitively dependent on the prime attributes。
Process：UNF →（Remove repeating groups）→ 1NF →（Remove partial dependencies）→ 2NF →（Remove transitive dependencies）→ 3NF。
课件例子：主键 (PROJ_NUM, EMP_NUM)；PROJ_NUM → PROJ_NAME 是部分依赖；EMP_NUM → EMP_NAME, JOB_CLASS, CHG_HOUR 是部分依赖；JOB_CLASS → CHG_HOUR 是传递依赖。2NF 拆成 ASSIGN(PROJ_NUM, EMP_NUM, HOURS)、PROJECT(PROJ_NUM, PROJ_NAME)、EMPLOYEE_JOB(EMP_NUM, EMP_NAME, JOB_CLASS, CHG_HOUR)；3NF 再把 EMPLOYEE_JOB 拆成 EMPLOYEE(EMP_NUM, EMP_NAME, JOB_CLASS) 和 JOB(JOB_CLASS, CHG_HOUR)。

**问题**：说一下第一、第二、第三范式

**答案要点**：
1. 1NF：每个单元格是原子值，每条记录唯一
2. 2NF：满足 1NF，非主属性完全依赖主键（消除部分依赖）
3. 3NF：满足 2NF，非主属性不传递依赖主键（消除传递依赖）
4. 部分依赖只在复合主键时才可能出现
5. 规范化过程：UNF → 1NF → 2NF → 3NF，每一步通过拆表实现

**对比**：
| 依赖类型 | 含义 | 课件例子 | 消除于 |
|---|---|---|---|
| 完全依赖 | 依赖整个主键 | (PROJ_NUM, EMP_NUM) → HOURS | 保留 |
| 部分依赖 | 只依赖复合主键的一部分 | PROJ_NUM → PROJ_NAME | 2NF |
| 传递依赖 | 通过非主属性间接依赖 | JOB_CLASS → CHG_HOUR | 3NF |

**常见陷阱**：
- ❌ 认为单列主键的表也可能存在部分依赖
- ✅ 主键只有一列时不存在"依赖一部分主键"，满足 1NF 就自动满足 2NF
- ❌ 把一列里存 "Java,Python" 这种逗号分隔的值当成正常设计
- ✅ 违反 1NF，应该拆到单独的表，每行一个值

**追问**：
- Q: 3NF 的表里，修改某个职位的时薪要改几处？
- A: 只改 JOB 表的一行；没拆之前，所有这个职位的员工行都要改，漏一行就是更新异常

**判断题**：
- ✅ 第二范式要求消除非主属性对主键的部分依赖 —— 非主属性必须完全依赖于整个主键
- ❌ 第三范式要求消除部分依赖 —— 消除部分依赖是 2NF；3NF 消除的是传递依赖

### 规范化的取舍

**概念**：规范化能减少冗余、避免异常、保证完整性，但会带来更多的表和 JOIN；有时会为了查询性能故意反规范化（denormalization）

**一句话**：规范化适合写操作多、每次只读少量数据、对数据完整性要求高的场景；缺点是设计成本高、表多、JOIN 代价大会拖慢查询；读多写少的报表、数据仓库常常反规范化，用一点冗余换更少的 JOIN。

**详细解释**：
Main goal of normalization：Reduce redundancy, avoid anomaly and create a well-structured series of table without error or inconsistencies；Minimize redesign when extending the database structure（New type of data can be accommodated without changing existing structure too much）；Ensure data dependencies are properly enforced by data integrity constraints (Entity Integrity, Referential Integrity, Domain Integrity)。
When do we normalize：Usually normalize in database with lots of writes；Not too much fetching or only fetch a small subset of the data；Data integrity is crucial。
Cons：Normalization is an expensive process；Designing can be difficult (Good for final design, not testing)；More tables leads to more time；Joins are costly, having more tables can cause slowing。
反规范化的常见做法：冗余存一个常用的名字字段、维护汇总表（比如订单总数），代价是要自己保证冗余数据同步。

**问题**：规范化有什么好处和坏处？什么时候会反规范化？

**答案要点**：
1. 好处：减少冗余、避免异常、扩展结构时少改动、保证完整性
2. 适合写多、读少量数据、强调完整性的场景
3. 坏处：设计成本高、表多、JOIN 多导致查询变慢
4. 读多写少（报表、数据仓库）常常反规范化，用冗余换查询速度
5. 反规范化后要自己保证冗余数据的一致性

**对比**：
| | 规范化 | 反规范化 |
|---|---|---|
| 冗余 | 少 | 多 |
| 写操作 | 简单、一致性好 | 要同步多处冗余数据 |
| 读操作 | 需要更多 JOIN | JOIN 少、查询快 |
| 适合 | 写多（OLTP） | 读多（报表、OLAP） |

**常见陷阱**：
- ❌ 认为范式越高越好，所有表都要拆到最细
- ✅ 要根据读写比例和性能需求权衡，实际项目一般做到 3NF 再按需反规范化

**追问**：
- Q: 电商的订单明细里为什么要冗余存一份商品名称和价格？
- A: 商品名称和价格以后可能会改，但订单要保留下单时的快照；同时也省掉了查询订单时的 JOIN

**判断题**：
- ✅ 表拆得越多，查询时需要的 JOIN 越多，可能导致查询变慢 —— 这是规范化的主要缺点
- ❌ 读多写少的数据仓库最适合严格规范化到 3NF 以上 —— 这类场景常常反规范化以减少 JOIN

### 数据完整性

**概念**：数据完整性（Data Integrity）是数据库保证数据正确、一致的一组规则，包括实体完整性、域完整性、参照完整性和用户定义完整性

**一句话**：实体完整性：主键不能为空、不能重复；域完整性：每列的取值要在合法范围内（类型、长度、NOT NULL、CHECK）；参照完整性：外键必须引用另一张表中存在的主键，被引用的行不能随便删；用户定义完整性：按业务规则自定义的约束。

**详细解释**：
Entity Integrity：Design of the table or entity；Strict PK with no nulls or repeats（课件原文写成 "String PK"）。
User-defined Integrity：Rules or constraints applied by the user to maintain rules of design。
Domain Integrity：Correct and proper domains specified with proper use of columns。
Referential Integrity：Proper FK setup with proper PK reference；Good design for connection and joins。
实现方式：主键约束 → 实体完整性；数据类型、NOT NULL、CHECK、DEFAULT → 域完整性；外键约束 → 参照完整性；CHECK、触发器、应用代码 → 用户定义完整性。
外键的行为：插入时引用的主键必须存在；删除被引用的父表记录时，默认会报错，也可以设置 ON DELETE CASCADE（级联删除）或 SET NULL。

**问题**：数据库的完整性有哪几种？分别靠什么保证？

**答案要点**：
1. 实体完整性：主键唯一且不为空，靠主键约束
2. 域完整性：列的取值合法，靠数据类型、NOT NULL、CHECK、DEFAULT
3. 参照完整性：外键必须引用存在的主键，靠外键约束
4. 用户定义完整性：业务规则，靠 CHECK、触发器或应用代码
5. 有外键引用时，删除父表记录默认会被拒绝，可配置级联删除

**对比**：
| 完整性 | 含义 | 实现方式 |
|---|---|---|
| 实体完整性 | 每行可唯一标识 | PRIMARY KEY |
| 域完整性 | 列值合法 | 类型、NOT NULL、CHECK、DEFAULT |
| 参照完整性 | 外键引用有效 | FOREIGN KEY |
| 用户定义完整性 | 业务规则 | CHECK、触发器、应用代码 |

**常见陷阱**：
- ❌ 只在应用代码里检查数据，数据库里不建任何约束
- ✅ 数据库约束是最后一道防线，绕过应用直接写库时也能保证数据正确

**追问**：
- Q: ON DELETE CASCADE 有什么风险？
- A: 删一条父记录会连带删除所有子记录，误删时影响范围很大；很多项目宁可用"逻辑删除"（加 deleted 标记）

**代码题**：下面 SQL 执行结果是什么？

```sql
CREATE TABLE products (id INT PRIMARY KEY, name VARCHAR(20));
CREATE TABLE orders (id INT PRIMARY KEY, product_id INT, FOREIGN KEY (product_id) REFERENCES products(id));
INSERT INTO products VALUES (1, 'pen');
INSERT INTO orders VALUES (100, 1);
INSERT INTO orders VALUES (101, 2);
SELECT COUNT(*) FROM orders;
```

- [ ] 2
- [ ] 1
- [x] 执行报错
- [ ] 查询结果为空

解析：订单 101 的 product_id = 2 在 products 表里不存在，违反参照完整性，外键约束让这条 INSERT 报错。

**代码题**：下面 SQL 执行结果是什么？

```sql
CREATE TABLE products (id INT PRIMARY KEY, name VARCHAR(20));
CREATE TABLE orders (id INT PRIMARY KEY, product_id INT, FOREIGN KEY (product_id) REFERENCES products(id));
INSERT INTO products VALUES (1, 'pen');
INSERT INTO orders VALUES (100, 1);
DELETE FROM products WHERE id = 1;
SELECT COUNT(*) FROM products;
```

- [ ] 0
- [ ] 1
- [x] 执行报错
- [ ] 查询结果为空

解析：products 里 id = 1 的行正被订单引用，默认的外键规则不允许删除被引用的父记录，DELETE 报错；需要先删子记录，或者给外键设置 ON DELETE CASCADE。

**判断题**：
- ✅ 实体完整性要求主键不能为 NULL 且不能重复 —— 这样每一行才能被唯一标识
- ❌ 参照完整性允许外键引用一个不存在的主键值 —— 外键的值必须在被引用的表中存在（或为 NULL）
